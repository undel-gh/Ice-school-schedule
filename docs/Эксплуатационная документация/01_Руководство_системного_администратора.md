# Руководство системного администратора

## 1. Назначение документа

Документ описывает развертывание, конфигурацию, обслуживание, обновление, резервное копирование, мониторинг и аварийное восстановление системы Ice School Schedule.

Текущая production-модель рассчитана на один Linux-сервер и использует Docker Compose. В состав входят:

- `proxy` — Caddy, публичные HTTPS/HTTP-порты и автоматическое получение TLS-сертификатов;
- `web` — Django под Gunicorn;
- `db` — PostgreSQL 17;
- `migrate` — одноразовый контейнер миграций, являющийся gate перед запуском приложения;
- `scheduler` — периодический запуск lifecycle и генерации занятий;
- `backup` — создание и проверка резервных копий PostgreSQL.

PostgreSQL и Gunicorn наружу не публикуются; публичный трафик должен входить через Caddy.

## 2. Требования к серверу

### 2.1. Программная платформа

Рекомендуется актуальный поддерживаемый Linux-дистрибутив. Для пилота подходит Debian/Ubuntu с установленными:

- Git;
- Docker Engine;
- Docker Compose plugin (`docker compose`);
- системным SSH-доступом для администратора;
- корректной синхронизацией времени.

Практический стартовый размер небольшого пилота — 1 vCPU, 2 ГБ RAM и 20 ГБ SSD. Это не жесткий системный минимум: место следует планировать с учетом журналов, PostgreSQL и локального хранения backup-файлов.

### 2.2. Сеть и DNS

До запуска Caddy должны быть готовы:

- публичная DNS-запись имени приложения;
- входящие TCP 80 и 443 до сервера;
- исходящий HTTPS для получения сертификатов и, если используются, OAuth/мониторинга;
- закрытый извне PostgreSQL.

Для тестового стенда и production следует использовать разные DNS-имена и разные секреты.

## 3. Подготовка учетной записи развертывания

Рекомендуется использовать отдельного непривилегированного пользователя, например `deploy`, с доступом к Docker. Репозиторий можно разместить, например, в `/opt/ice-school-schedule`.

Пользователь развертывания должен иметь право:

- читать/обновлять Git-репозиторий;
- запускать `docker compose`;
- читать `.env.production`;
- контролировать каталог локальных резервных копий.

Файл `.env.production` не должен быть доступен посторонним пользователям ОС.

Важно: текущий контейнер `backup` работает от root, а `umask 077` приводит к созданию dump-файлов обычно как `root:root 0600`. Поэтому обычный пользователь `deploy` может видеть имена файлов в каталоге, но не читать их напрямую. Для off-host копирования используйте `sudo` либо читайте архив через контейнер `backup`; не ослабляйте права на backup-файлы ради удобства.

## 4. Первичное развертывание

### 4.1. Получение приложения

```bash
git clone https://github.com/undel-gh/Ice-school-schedule.git /opt/ice-school-schedule
cd /opt/ice-school-schedule
```

Перед production-развертыванием рекомендуется зафиксировать конкретный проверенный commit/tag, а не развертывать произвольный незавершенный branch.

### 4.1.1. Автоматизированный production lifecycle (предпочтительный способ)

Скрипт `install.sh` запускается из доверенного Git checkout от технической учётной записи с правом доступа к Docker Engine (приравнивается к root). Требуются Bash, Git, Docker Engine, Compose v2+ (рекомендуется Compose ≥2.24 для согласованной обработки кавычек в `.env.production`). Скрипт управляет **существующими** `compose.production.yaml` / migrate / web / scheduler / backup / Caddy, не создавая второго deployment stack.

Первый вызов:

~~~bash
./install.sh install
~~~

Если `.env.production` отсутствует, создаётся `.env.production` из `.env.production.example` с правами 0600, после чего скрипт **останавливается**, чтобы администратор безопасно установил реальные ключи и проверил DNS/80/443. Примерные пароли и `school.example.com` не принимаются. Отредактируйте env, установите права `chmod 600 .env.production`, затем повторите `./install.sh install`. Приложение запускается после validation Compose, сборки образа, успешной миграции и проверки Docker web healthcheck.

Обслуживание:

~~~bash
./install.sh status
./install.sh update
./install.sh update --ref v1.2.3
./install.sh reinstall
./install.sh uninstall
~~~

- `status`: SHA checkout, Compose services, Docker health db/web/scheduler/backup, состояние proxy; возвращает ошибку, если web не healthy.
- `update`: требует чистое Git working tree и healthy DB; делает верифицированный on-host PostgreSQL backup **до** fetch/checkout; получает refs из `origin`; по умолчанию использует `origin/main`, `--ref` принимает tag, commit или remote branch; строит новый image под отдельным временным тегом `candidate-<SHA>-<PID>`, проводит `migrate` на candidate и **только после успеха** присваивает рабочий `APP_IMAGE_TAG` (по умолчанию `local`) перед пересозданием `web`, `scheduler`, `backup`, `proxy`. Неудачные build/migrate не заменяют действующий release-тег. После успешной операции и на аварийном выходе скрипт пытается удалить только временный candidate-тег через `docker image rm`; ошибка очистки выводится как предупреждение и не меняет результат операции. Состояние DB volume не удаляется. При ошибке до начала migration gate git checkout автоматически возвращается на прежний SHA; после начала миграций автоматического rollback кода/схемы нет. После успешного `update` checkout остаётся в состоянии **detached HEAD** — это ожидаемо; следующий update снова fetch/checkout.
- `reinstall`: требует работающую БД, создаёт проверенный backup и пересобирает stack с текущего SHA без изменения данных; не выполняет очистку named volumes.
- `uninstall`: `docker compose down --remove-orphans` без удаления persistent volumes, `.env.production` и host backup-файлов.
- `uninstall --purge-data`: **опасная отдельная операция**. Требует терминала и точного ввода `PURGE <APP_HOST>`, вызывает `docker compose down --remove-orphans --volumes`. Это уничтожает PostgreSQL и Caddy **именованные тома**, но **не удаляет** bind-mounted host backup-файлы и `.env.production`. Никогда не используйте для обновления или переустановки.

В сценарии обновления сервис `backup` запускает имеющийся `ops/postgres_backup.sh --once`, который проверяет дамп через `pg_restore --list`. Отказ в создании backup, ошибочный build, некорректный Compose или failed migrations **прерывают rollout**. Бэкап остаётся локальным/незашифрованным; требование off-site encrypted backup выполняется отдельно в Issue #35. При schema migrations, несовместимых со старым запущенным кодом, требуется окно обслуживания: до переключения web может продолжать работать старая версия на изменяющейся схеме. Универсальный откат после успешных миграций не обещается; используйте forward-fix, проверенные backups и документированный restore.

**Ручной fallback:** если скрипт недоступен, используйте candidate workflow из раздела 9 (backup → build candidate → migrate → release-tag promotion → rollout). Не пересобирайте активный тег до успеха миграций. Раздел 4.5 описывает только **чистую первую установку на пустой БД**; не заменяйте fallback слепым `git pull && docker compose up -d`.

### 4.2. Production-конфигурация

Создайте рабочий env-файл из примера:

```bash
cp .env.production.example .env.production
chmod 600 .env.production
```

Создайте каталог резервных копий:

```bash
mkdir -p backups
chmod 700 backups
```

Минимально необходимо изменить:

- `APP_HOST` — публичное DNS-имя;
- `DJANGO_ALLOWED_HOSTS` — разрешенное имя приложения;
- `DJANGO_SECRET_KEY` — длинный случайный секрет;
- `POSTGRES_PASSWORD` — длинный случайный пароль БД;
- `SCHOOL_TIME_ZONE` — локальная IANA timezone школы, например `Europe/Riga`;
- параметры OAuth, если включен вход через Яндекс/VK.

Секрет Django можно создать локально:

```bash
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

Секреты не следует передавать в чаты, тикеты и журналы CI и нельзя коммитить в Git.

### 4.3. Параметры `.env.production`

Актуальным источником полного перечня переменных остается `.env.production.example`. Ниже перечислены параметры, которые особенно важны для эксплуатации.

#### Host, Django и timezone

```text
APP_HOST=school.example.com
APP_IMAGE_TAG=local
DJANGO_DEBUG=0
DJANGO_ALLOWED_HOSTS=school.example.com
SCHOOL_TIME_ZONE=Europe/Riga
DJANGO_TIME_ZONE=UTC
```

`APP_HOST` используется Caddy и healthcheck приложения. `DJANGO_ALLOWED_HOSTS` должен включать публичное имя.

`SCHOOL_TIME_ZONE` — локальная timezone школы и бизнес-расписания. `DJANGO_TIME_ZONE` — базовая timezone Django; штатная production-конфигурация может оставлять ее `UTC`.

`APP_IMAGE_TAG` задает tag общего application image `ice-school-app:<tag>`, который используют `migrate`, `web` и `scheduler`. Если параметр не задан, Compose использует `local`.

#### Django и безопасность

```text
DJANGO_SECURE_SSL_REDIRECT=1
DJANGO_SECURE_HSTS_SECONDS=3600
DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=0
DJANGO_SECURE_HSTS_PRELOAD=0
TRUSTED_PROXY_IPS=172.30.0.10
AXES_FAILURE_LIMIT=5
```

`TRUSTED_PROXY_IPS` должен соответствовать адресу доверенного reverse proxy. По умолчанию production Compose закрепляет Caddy за `172.30.0.10`. Если изменяется subnet Compose, нужно одновременно изменить доверенный адрес в Django.

HSTS `includeSubDomains` и `preload` следует включать только после подтверждения, что домен и затрагиваемые поддомены постоянно работают по HTTPS. Не следует включать preload только ради устранения предупреждения `check --deploy`.

#### MFA

```text
MFA_PREAUTH_TTL_SECONDS=300
MFA_PRIVILEGED_SESSION_MAX_AGE_SECONDS=43200
MFA_TOTP_ISSUER='Ice School'
```

MFA обязательно для `is_staff`, `is_superuser` и пользователей, которым выданы manager-operation permissions. Для таких учетных записей внешний вход через Яндекс/VK запрещен: используется локальный пароль + TOTP.

Для **обычных** пользователей с usable local password MFA опционален. Наличие подтверждённого TOTP включает второй фактор именно для локального password-login. OAuth-сессии обычных пользователей помечаются отдельно и не требуют TOTP только из-за наличия локального пароля или TOTP. Сессии с локальным входом без MFA после включения TOTP не сохраняют доступ без повторной проверки. Управление включением, recovery codes, заменой и отключением доступно пользователю через «Защита входа». Отключение требует повторной проверки локального пароля и одноразового кода; для privileged аккаунта не разрешено.

#### Внешняя аутентификация и приглашения

```text
EXTERNAL_AUTH_FLOW_TTL_SECONDS=600
EXTERNAL_AUTH_HTTP_TIMEOUT_SECONDS=10
ACCOUNT_INVITATION_TTL_HOURS=168
```

`EXTERNAL_AUTH_FLOW_TTL_SECONDS` ограничивает время жизни промежуточного OAuth flow/state. `EXTERNAL_AUTH_HTTP_TIMEOUT_SECONDS` задает timeout исходящих HTTP-запросов к OAuth-провайдерам. `ACCOUNT_INVITATION_TTL_HOURS` задает срок действия одноразового приглашения; значение по умолчанию в production example — 168 часов.

#### Gunicorn

```text
GUNICORN_WORKERS=3
GUNICORN_TIMEOUT_SECONDS=30
```

`GUNICORN_WORKERS` задает число worker-процессов web-контейнера. Для маломощного пилотного VPS допустимо осознанно уменьшить значение, например до `1`. `GUNICORN_TIMEOUT_SECONDS` — timeout worker request в секундах.

#### Scheduler

По умолчанию:

```text
process_subscription_lifecycle           каждые 3600 секунд
generate_lessons --all-active --horizon-days 60
                                         каждые 21600 секунд
```

Параметры:

```text
SCHEDULER_LIFECYCLE_INTERVAL_SECONDS
SCHEDULER_GENERATION_INTERVAL_SECONDS
SCHEDULER_GENERATION_HORIZON_DAYS
SCHEDULER_LIFECYCLE_TIMEOUT_SECONDS
SCHEDULER_GENERATION_TIMEOUT_SECONDS
SCHEDULER_HEALTH_GRACE_SECONDS
SCHEDULER_LIFECYCLE_SUCCESS_PING_URL
SCHEDULER_GENERATION_SUCCESS_PING_URL
```

Scheduler должен работать **в одном экземпляре**. Не масштабируйте этот сервис выше одной replica.

#### Backup и monitoring HTTP

```text
BACKUP_HOST_PATH=./backups
BACKUP_INTERVAL_SECONDS=86400
BACKUP_TIMEOUT_SECONDS=3600
BACKUP_RETENTION_DAYS=14
BACKUP_SUCCESS_PING_URL=
MONITORING_HTTP_TIMEOUT_SECONDS=10
```

`MONITORING_HTTP_TIMEOUT_SECONDS` задает timeout исходящих success-ping запросов scheduler/backup. Failure отправки ping логируется отдельно и не превращает уже успешно выполненную бизнес-операцию или backup в неуспешную.

Локальный backup не считается полноценной стратегией резервирования. Проверенные дампы необходимо регулярно копировать в защищенное off-host хранилище.

#### Docker logging

```text
DOCKER_LOG_MAX_SIZE=10m
DOCKER_LOG_MAX_FILES=5
```

Эти параметры ограничивают ротацию `json-file` логов каждого production-контейнера.

### 4.4. Внешняя аутентификация

При необходимости настройте Яндекс и/или VK ID:

```text
YANDEX_OAUTH_CLIENT_ID=
YANDEX_OAUTH_CLIENT_SECRET=
YANDEX_OAUTH_SCOPE=login:info

VKID_CLIENT_ID=
VKID_SCOPE=
```

Callback URLs должны **точно** соответствовать production-origin и фактическому маршруту приложения:

```text
https://<school-host>/accounts/external/callback/yandex/
https://<school-host>/accounts/external/callback/vk/
```

Неправильный порядок сегментов URL приведет к отказу OAuth-провайдера из-за несовпадения `redirect_uri`.

Обычные ученики, родители и тренеры подключаются по одноразовым приглашениям. Неизвестная внешняя учетная запись не может сама зарегистрироваться через обычную страницу входа.

### 4.5. Проверка Compose и сборка

Этот ручной порядок допустим только для **новой пустой БД**. При повторной установке с сохранённой БД используйте `./install.sh install` либо candidate workflow раздела 9 с предварительным backup.

Перед запуском:

```bash
docker compose --env-file .env.production -f compose.production.yaml config >/dev/null
```

Сборка:

```bash
docker compose --env-file .env.production -f compose.production.yaml build
```

Запуск:

```bash
docker compose --env-file .env.production -f compose.production.yaml up -d
```

Порядок запуска предусмотрен в Compose:

1. PostgreSQL становится healthy;
2. `migrate` применяет миграции и завершается с кодом 0;
3. запускается `web` и проходит `/healthz/`;
4. запускается Caddy;
5. запускаются scheduler и backup.

Проверка:

```bash
docker compose --env-file .env.production -f compose.production.yaml ps -a
```

Нормальное состояние:

- `db`, `web`, `scheduler`, `backup` — healthy;
- `proxy` — running/up;
- `migrate` — `Exited (0)`.

### 4.6. Проверка приложения

```bash
curl -fsS https://<school-host>/healthz/ ; echo
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Проверьте production settings:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec -T web python manage.py check --deploy
```

Проверьте миграции:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec -T web python manage.py showmigrations
```

## 5. Создание первой привилегированной учетной записи

Создайте локального superuser внутри приложения:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec web python manage.py createsuperuser
```

Не используйте для сотрудников общий аккаунт. У каждого менеджера/администратора должна быть собственная учетная запись.

При первом успешном входе привилегированный пользователь обязан зарегистрировать TOTP. Система показывает QR/секрет и 10 одноразовых recovery-кодов. Recovery-коды нужно сохранить вне браузерной сессии в защищенном хранилище.

TOTP-код защищен от replay: уже использованный код в том же 30-секундном окне нельзя применять повторно. При немедленном повторном входе дождитесь следующего кода.

### Обычные пользователи без Яндекс/VK

Публичная регистрация локальных пользователей не вводится. Администратор может создать обычного пользователя через Django Admin в разделе Users, задать ему собственный локальный пароль и убедиться, что `is_staff`, `is_superuser` и manager-operation permissions не выставлены. Менеджер привязывает этого User к ученику (StudentAccess) или создаёт CoachProfile через существующий web-интерфейс. Не используйте общий тестовый аккаунт с реальными персональными данными.

Обычный локальный пользователь сразу может войти по username/password, а TOTP при желании включает самостоятельно. Для OAuth-only аккаунтов пароль по-прежнему unusable: они не могут войти локально, пока пароль не будет установлен администратором. Не передавайте сгенерированный пароль в открытом канале и не меняйте его без согласованного процесса восстановления.

## 6. Регулярное обслуживание

### 6.1. Ежедневный/периодический контроль

Администратору рекомендуется контролировать:

- `https://<school-host>/healthz/`;
- `docker compose ... ps -a`;
- свободное место (`df -h`);
- наличие свежего `.dump`;
- состояние scheduler/backup healthcheck;
- ошибки `web`, `proxy`, `scheduler`, `backup`;
- успешность внешних dead-man checks, если они настроены.

Просмотр журналов:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  logs --since 24h web proxy scheduler backup
```

Docker-логи ограничены ротацией. Значения по умолчанию:

```text
DOCKER_LOG_MAX_SIZE=10m
DOCKER_LOG_MAX_FILES=5
```

Caddy специально не пишет request-target для URL, содержащих чувствительные одноразовые токены или OAuth callback-параметры. Не удаляйте исключения для invitation/callback/reset путей при изменении logging-конфигурации.

### 6.2. Внешний мониторинг

Локальный Docker healthcheck сам по себе не отправляет уведомления и не гарантирует перезапуск unhealthy-контейнера. Рекомендуются:

- внешний HTTPS uptime check `/healthz/`;
- dead-man check для lifecycle job;
- dead-man check для генерации занятий;
- dead-man check для backup.

Для success ping используются:

```text
SCHEDULER_LIFECYCLE_SUCCESS_PING_URL
SCHEDULER_GENERATION_SUCCESS_PING_URL
BACKUP_SUCCESS_PING_URL
MONITORING_HTTP_TIMEOUT_SECONDS
```

URL success ping являются bearer-like секретами и не должны попадать в Git/логи.

## 7. Резервное копирование

Backup-контейнер создает custom-format PostgreSQL dump. Алгоритм:

1. `pg_dump` пишет файл с суффиксом `.partial`;
2. архив проверяется `pg_restore --list`;
3. только валидный архив атомарно переименовывается в `.dump`;
4. обновляется marker последнего успеха;
5. применяются правила retention.

Файлы создаются с `umask 077`. В текущем Compose это обычно означает `root:root 0600`, потому что контейнер `backup` не переключен на непривилегированного пользователя.

Принудительная дополнительная копия:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec backup /ops/postgres_backup.sh --once
```

После команды проверьте появление нового `.dump` и отсутствие `.partial`.

### 7.1. Автоматизированное client-side encryption и S3 off-site

Исходный локальный backup в `/backups/` хранится **незашифрованным** (`root:root 0600`) для быстрого восстановления. Для защиты от потери VPS включается **отдельный**, ограниченный Compose overlay `compose.offsite.yaml`. Он запускает `offsite-backup` (Restic на Alpine) и автоматически переносит свежие завершённые дампы `ice_school_*.dump` в **зашифрованный на клиенте** Restic repository по HTTPS. Файлы `*.partial` никогда не отправляются. Репозиторий должен находиться **вне VPS и его дисков/snapshots**.

Шифрование Restic обеспечивается паролем repository, который **не передаётся S3**. Для дешифрования на чистом сервере нужны и доступ к S3, и независимая сохранённая копия пароля. Один потерянный пароль означает безвозвратную потерю возможности восстановить архив. Нельзя хранить единственную копию пароля или S3 recovery credentials на том же VPS, который защищается. Храните копию в корпоративном сейфе/secret manager вне хоста и проверьте процедуру выдачи доступа.

**Подготовка хранилища:**

1. Создайте отдельный private bucket S3-compatible у внешнего провайдера, выделенный prefix (например `school-prod/restic`), запретите публичный доступ. Используйте HTTPS с валидным TLS и scoped S3 ключом только для этого bucket/prefix. Restic retention `forget --prune` требует List/Get/Put/Delete; учитывайте риск удаления злоумышленником при компрометации VPS. По возможности настройте bucket versioning/Object Lock/immutable retention или независимые внешние копии; политику хранения S3 согласуйте с `restic forget --prune`.
2. Создайте два секретных файла **вне** Git checkout и `/backups/`: например `/etc/ice-school-secrets/restic-password` (криптографически случайная парольная фраза длиной не менее 32 случайных байт) и `/etc/ice-school-secrets/aws-credentials`. Оба должны быть обычными файлами, **не symlink**, разрешение `0600`; родительский каталог `0700`, доступен только доверенному deploy/root. Не передавайте содержимое в GitHub/тикеты/чаты и не включайте в резервные копии того же репозитория.
3. Содержимое `aws-credentials` — стандартный AWS shared credentials file:

~~~ini
[default]
aws_access_key_id = <scoped-access-key-id>
aws_secret_access_key = <scoped-secret-access-key>
~~~

4. Добавьте в `.env.production` (файл `0600`) параметры, без самих секретов:

~~~dotenv
OFFSITE_ENABLED=1
OFFSITE_RESTIC_REPOSITORY=s3:https://s3.example.net/school-prod/restic
OFFSITE_RESTIC_PASSWORD_HOST_FILE=/etc/ice-school-secrets/restic-password
OFFSITE_AWS_CREDENTIALS_HOST_FILE=/etc/ice-school-secrets/aws-credentials
OFFSITE_RESTIC_HOST=ice-school-production
OFFSITE_POLL_SECONDS=300
OFFSITE_KEEP_DAILY=14
OFFSITE_KEEP_WEEKLY=8
OFFSITE_KEEP_MONTHLY=12
# Настроить отдельный dead-man monitoring endpoint, не совпадающий с локальным.
OFFSITE_SUCCESS_PING_URL=
~~~

5. **Однократно вручную** инициализируйте ещё пустой Restic repository (инсталлятор не инициализирует его молча). Проверьте URL и пароль до выполнения:

~~~bash
docker compose --env-file .env.production \
  -f compose.production.yaml -f compose.offsite.yaml \
  build offsite-backup

docker compose --env-file .env.production \
  -f compose.production.yaml -f compose.offsite.yaml \
  run --rm --no-deps -T --entrypoint restic offsite-backup init
~~~

Если repository уже существует, **не запускайте** `restic init` повторно; проверьте доступ через `restic snapshots`. После этого запустите `./install.sh install` для новой установки либо `./install.sh update` для существующей. Последняя операция создаёт новый проверенный локальный dump и **синхронно** отправляет его в S3 **до Git checkout, build приложения или миграций**. Ошибка off-site выгрузки прерывает update/reinstall до изменения БД.

Sidecar периодически ищет последний завершённый дамп (по умолчанию раз в 300 секунд), шифрует его и создаёт Restic snapshot. Повторная отправка того же имени не выполняется, пока зафиксировано успешное завершение upload и retention. Метки `last_success` и `last_uploaded` сохраняются в Docker volume `offsite_status`. Политика `forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune --group-by host,tags` не группирует разные файлы по уникальным путям; она применяется только к `--host ice-school-production --tag ice-school-postgres`. Применение retention требует доступа на удаление в S3. `restic check --read-data` запускается отдельно по расписанию restore-упражнений: не читайте весь S3-репозиторий каждую ночь без необходимости.

**Мониторинг и отказ:** `./install.sh status` требует healthy у `offsite-backup`, когда `OFFSITE_ENABLED=1`. Новый сбой выгрузки или retention немедленно создаёт `last_failure` и переводит off-site healthcheck в `unhealthy`, даже если предыдущая успешная отправка была недавно. После успешного повтора ошибка снимается. Health marker также перестаёт быть актуальным, если успешных передач нет более `2 × BACKUP_INTERVAL_SECONDS + OFFSITE_HEALTH_GRACE_SECONDS`; при неудаче отправки пишется событие `offsite event=failed stage=restic_backup`/`restic_retention`. Настройте алерты на container unhealthy/exit и отдельный dead-man monitor `OFFSITE_SUCCESS_PING_URL` на ожидаемую частоту backup (не на локальный marker). Ping **отправляется только после успешной передачи и retention**, а его неудача логируется отдельно. Ошибка ping не отменяет уже подтверждённую зашифрованную копию.

Операция `uninstall` по умолчанию не удаляет named volume состояния offsite. `--purge-data` уничтожает **все именованные volumes Compose**, включая состояние offsite, но **не удаляет** внешний S3-репозиторий и секретные файлы на хосте. Изменение `OFFSITE_ENABLED` с `1` на `0` отключает проверку offsite, но **не доказывает**, что прежний sidecar остановлен: управляйте его остановкой явно и проверяйте контейнеры. Не используйте отключение мониторинга как решение аварии S3.

### 7.2. Реальное восстановление с чистого сервера

Не менее ежеквартально (и после изменений ключей/storage/retention) выполняйте отдельный сценарий полного восстановления **без доступа к исходному VPS и локальным `/backups/`**:

1. На изолированном test/DR хосте установите Docker/Restic и настройте только read-only S3 доступ, отдельную копию пароля из внешнего secret manager. Не используйте хост с production Postgres и не открывайте восстановленные персональные данные публично.
2. Проверьте `restic snapshots` и `restic check --read-data` (для очень большого репозитория допустима ротационная `--read-data-subset`, но полный check должен периодически проводиться).
3. Выберите требуемый snapshot, узнайте путь внутри него через `restic ls <snapshot-id>` и выгрузите один dump без дополнительных исходных файлов:

~~~bash
umask 077
# Пример для отдельного проверенного Restic окружения на DR-хосте:
restic snapshots --host ice-school-production --tag ice-school-postgres
restic ls <snapshot-id>
restic dump <snapshot-id> /backups/ice_school_YYYYMMDDTHHMMSSZ.dump \
  > /secure/recovery/ice_school_restore.dump
pg_restore --list /secure/recovery/ice_school_restore.dump >/dev/null
~~~

4. Восстановите дамп **в новую пустую PostgreSQL 17 БД** через `pg_restore --no-owner --no-privileges`, проверьте число записей `django_migrations` и согласованные бизнес-сущности через тестовое приложение. Проводите функциональную проверку входа, ролей, расписания, абонементов и MFA. Не перезаписывайте production DB в рамках учения.
5. Зафиксируйте snapshot ID, время создания, результат check/restore, RPO/RTO, ответственного; удалите тестовые данные по регламенту. Только успешное проверенное восстановление закрывает критерий готовности DR.

### 7.3. Ручной off-host экспорт (аварийный fallback)


Не делайте `chmod 644` backup-файлам. Для переноса используйте один из безопасных вариантов:

```bash
# вариант 1: системный администратор читает файл через sudo
sudo cp backups/ice_school_YYYYMMDDTHHMMSSZ.dump /secure/staging/
```

или потоково читайте файл через контейнер, который уже имеет доступ к `/backups`:

```bash
BACKUP_FILE=ice_school_YYYYMMDDTHHMMSSZ.dump

docker compose --env-file .env.production -f compose.production.yaml \
  run --rm --no-deps -T backup cat "/backups/$BACKUP_FILE" \
  > "/secure/staging/$BACKUP_FILE"
```

Дальше копируйте staging-файл в шифрованное/off-host хранилище по политике организации и удаляйте временную локальную копию после проверки передачи.

Регулярно выполняйте тест восстановления. Наличие файла само по себе не подтверждает работоспособность backup-стратегии.

## 8. Восстановление PostgreSQL

> Восстановление является разрушительной операцией. Перед началом зафиксируйте текущую версию приложения, выбранный backup и причину восстановления.

Остановите writers:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  stop proxy web scheduler backup
```

Загрузите переменные:

```bash
set -a
source .env.production
set +a
```

Выберите архив:

```bash
BACKUP_FILE=ice_school_YYYYMMDDTHHMMSSZ.dump
```

Восстановите:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  run --rm --no-deps -T backup cat "/backups/$BACKUP_FILE" | \
  docker compose --env-file .env.production -f compose.production.yaml \
  exec -T db pg_restore \
    --clean --if-exists --no-owner --no-privileges \
    -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Затем примените миграции текущего image и поднимите сервисы:

```bash
docker compose --env-file .env.production -f compose.production.yaml run --rm migrate

docker compose --env-file .env.production -f compose.production.yaml \
  up -d web scheduler backup proxy
```

После восстановления обязательно проверить:

- `/healthz/`;
- вход привилегированного пользователя и MFA;
- расписание;
- карточку абонемента;
- несколько последних AuditEvent;
- состояние scheduler и backup.

## 9. Обновление приложения

Для обычного production update используйте прежде всего `./install.sh update` или `./install.sh update --ref <tag|commit|branch>` из раздела 4.1.1. Ниже приведена ручная fallback-процедура с проверкой миграционного gate.

### 9.1. Подготовка

Перед обновлением:

```bash
cd /opt/ice-school-schedule
git status --short
```

Рабочее дерево production checkout должно быть чистым. Не используйте ручные постоянные исправления в файлах на сервере: изменения должны приходить из Git.

Перед **каждым** ручным обновлением создайте проверенный backup и прекращайте процесс при ошибке:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  run --rm --no-deps -T backup /ops/postgres_backup.sh --once
```

### 9.2. Получение новой версии

```bash
git fetch --prune --tags origin
git checkout --detach origin/main  # либо проверенный tag/commit
git rev-parse HEAD
```

Сверьте SHA с ожидаемым merge/tag. После первого обновления скриптом рабочий checkout остаётся **detached HEAD**; `git pull` без ветки не подходит, это штатно.

### 9.3. Сборка candidate image

Вручную определите действующий `APP_IMAGE_TAG` из `.env.production` (по умолчанию `local`), не выполняя `source` с секретами. **Нельзя** собирать новый образ под работающим тегом до успешных миграций.

```bash
RELEASE_TAG=local  # если .env.production задаёт другой APP_IMAGE_TAG, измените
CANDIDATE_TAG="candidate-$(git rev-parse --short=12 HEAD)-manual-$$"
export APP_IMAGE_TAG="$CANDIDATE_TAG"
docker compose --env-file .env.production -f compose.production.yaml build migrate
```

### 9.4. Миграции

Одноразовый migration gate выполняется **на candidate image**:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  run --rm --no-deps -T migrate
```

При ненулевом коде возврата **остановитесь**. Действующий `ice-school-app:$RELEASE_TAG` не изменён, и нельзя запускать новый `web`. БД могла частично измениться — изучите раздел 10.

### 9.5. Переключение release-тега и перезапуск

**Только после** успешного gate:

```bash
docker image tag "ice-school-app:$CANDIDATE_TAG" "ice-school-app:$RELEASE_TAG"
export APP_IMAGE_TAG="$RELEASE_TAG"
docker compose --env-file .env.production -f compose.production.yaml \
  up -d --no-deps --force-recreate web scheduler backup
docker compose --env-file .env.production -f compose.production.yaml \
  up -d --no-deps --force-recreate proxy
```

Ручные команды требуют проверки exit code **каждого** шага (`set -e` или отдельные проверки). Ошибка миграций не должна приводить к `docker compose up -d`. Скрипт `./install.sh update` автоматизирует эту безопасную последовательность.

Итоговая проверка:

```bash
docker compose --env-file .env.production -f compose.production.yaml ps -a
curl -fsS https://<school-host>/healthz/ ; echo
```

После обновления рекомендуется выполнить web smoke-test: вход, главная страница нужной роли, расписание, manager dashboard и несколько измененных страниц.

## 10. Rollback и неудачное обновление

Не следует считать возврат старого Docker image универсальным rollback для обновления с миграциями. Если migration изменила схему несовместимым образом, rollback должен следовать инструкции конкретной миграции или выполняться через forward-fix/restore backup.

Если миграция не прошла:

1. не запускайте новый `web`;
2. сохраните вывод `migrate`;
3. определите, были ли частично применены migrations;
4. устраните причину в коде или восстановите БД согласно плану изменения;
5. повторите migration gate.

## 11. Scheduler и конфликты генерации

Scheduler периодически создает будущие занятия по активным шаблонам. Конфликт регулярного слота с занятием другого типа считается ошибкой генерации и отражается в manager web UI как «Конфликты генерации».

Не лечите бизнес-конфликт перезапуском контейнера или прямой правкой БД. Менеджер должен разрешить ситуацию через интерфейс: изменить расписание либо явно пропустить конкретное регулярное занятие.

Ручная диагностика:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec scheduler python manage.py process_subscription_lifecycle

docker compose --env-file .env.production -f compose.production.yaml \
  exec scheduler python manage.py generate_lessons --all-active --horizon-days 60
```

## 12. Аварийное восстановление MFA

Если привилегированный пользователь потерял TOTP и все recovery-коды, используйте server-side break-glass механизм `django-otp`:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec web python manage.py addstatictoken -h
```

Создайте одноразовый static token по инструкции команды. После входа пользователь должен зарегистрировать новый TOTP. Не отключайте MFA middleware как метод восстановления.

Для смены локального пароля:

```bash
docker compose --env-file .env.production -f compose.production.yaml \
  exec web python manage.py changepassword <username>
```

## 13. Восстановление внешней учетной записи ученика/родителя/тренера

При компрометации единственного внешнего провайдера бизнес-процесс выполняет менеджер:

1. деактивирует внутреннего пользователя;
2. отвязывает скомпрометированный ExternalIdentity;
3. создает recovery-приглашение на **тот же User**;
4. передает ссылку независимым доверенным каналом;
5. пользователь входит через новый/восстановленный Яндекс/VK;
6. существующий User реактивируется без потери связей и истории.

Системный администратор не должен создавать новый User вручную вместо этого процесса, если web workflow исправен.

## 14. Границы ответственности администратора

Системный администратор отвечает за доступность и техническую целостность платформы, но не должен обходить application services прямыми изменениями бизнес-таблиц PostgreSQL/Django Admin.

Обычные операции менеджера и тренера выполняются через web-интерфейс. Management commands предназначены для автоматизации, диагностики и аварийных/специально разрешенных административных действий, а не как основной UI.

При расследовании инцидентов сохраняйте:

- SHA развернутого commit;
- время события и timezone;
- состояние контейнеров;
- релевантные журналы;
- AuditEvent/идентификаторы объектов;
- факт и время последнего проверенного backup.
