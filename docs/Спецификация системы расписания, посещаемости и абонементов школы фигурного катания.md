# Спецификация системы расписания, посещаемости и абонементов школы фигурного катания

**Версия:** 1.0  
**Стек:** Django + PostgreSQL + Django Admin + server-rendered frontend  
**Статус:** базовая спецификация MVP с возможностью дальнейшего расширения

---

# 1. Назначение системы

Система предназначена для организации расписания занятий школы фигурного катания, предварительного подтверждения участия учениками/родителями, фиксации фактической посещаемости тренерами и учёта абонементов.

Система должна заменить существующую схему, при которой расписание публикуется в чате, а участники ставят `+` или `-`.

Основные задачи:

1. Ведение групп, тренеров и расписания.
2. Публикация персонального расписания для каждого участника.
3. Возможность заранее отметить:
   - «Буду»;
   - «Не буду».
4. Отображение организатору ожидаемого количества участников.
5. Фиксация тренером фактического присутствия.
6. Учёт абонементов с ограниченным количеством занятий и сроком действия.
7. Автоматическое списание занятия из абонемента при фактическом посещении.
8. Отображение остатка абонемента.
9. Минимизация объёма персональных данных.
10. Возможность в будущем подключить оплату, не меняя основную архитектуру.

---

# 2. Основные принципы

## 2.1. Фактическое посещение отделяется от намерения прийти

В системе существуют два независимых понятия.

### RSVP

Ответ пользователя до занятия:

- буду;
- не буду;
- нет ответа.

RSVP используется для планирования количества участников.

Он **не списывает занятие из абонемента**.

### Attendance

Фактическая отметка тренера:

- присутствовал;
- отсутствовал;
- не отмечено.

Именно фактическое присутствие является основанием для расходования занятия из абонемента.

Таким образом:

```text
«Буду» → занятие не списывается.

Тренер отметил «Пришёл» → занятие списывается.
```

# 3. Архитектура

Система реализуется как единое Django-приложение.

```text
                  Пользователь
             телефон / ПК / планшет
                       │
                     HTTPS
                       │
                       ▼
              ┌─────────────────┐
              │     Django      │
              │                 │
              │ Server-rendered │
              │    frontend     │
              │                 │
              │  Business logic │
              │                 │
              │  Django Admin   │
              └────────┬────────┘
                       │
                       ▼
               ┌──────────────┐
               │ PostgreSQL   │
               └──────────────┘
```

Отдельное SPA на React/Vue в первой версии не требуется.

Frontend реализуется через:

- Django Templates;
- HTML;
- CSS;
- минимальный JavaScript;
- при необходимости HTMX.

Это уменьшает:

- количество компонентов;
- объём JavaScript;
- сложность авторизации;
- количество API;
- поверхность атаки;
- стоимость сопровождения.

# 4. Пользовательские роли

## 4.1. Участник / родитель

Может:

- войти через внешний Identity Provider;
- видеть расписание связанных с аккаунтом участников;
- переключаться между детьми, если их несколько;
- ставить «Буду» / «Не буду»;
- видеть состояние своего абонемента;
- видеть количество оставшихся занятий;
- видеть срок действия абонемента;
- видеть историю собственных посещений.

Не может:

- видеть других участников;
- видеть списки группы;
- изменять фактическую посещаемость;
- изменять абонемент.

---

# 5. Родитель и ребёнок

Учётная запись и занимающийся человек должны быть разными сущностями.

Например:

```text
Account
   │
   ├── Маша
   │     └── группа «Начальная 1»
   │
   └── Петя
         └── группа «Подготовительная»
```

Это позволяет использовать один аккаунт родителя для нескольких детей.

Отдельная учётная запись ребёнку не требуется.

Также допускается:

```text
Account → Participant
```

когда совершеннолетний участник самостоятельно пользуется системой.

---

# 6. Тренер

Тренер должен иметь специализированный интерфейс, не требующий работы непосредственно с Django Admin.

Тренер может:

- видеть сегодняшние занятия;
- видеть назначенные ему занятия;
- видеть участников соответствующей группы;
- видеть RSVP;
- отмечать фактическое присутствие;
- исправлять ошибочно поставленную отметку в пределах разрешённого периода.

Например:

```text
Лёд
14 сентября
17:00–18:00

Ожидалось: 12

─────────────────────────
Маша             ✓ Пришла
Катя              ✓ Пришла
Саша              ○ Отметить
Ира               ✕ Нет
Петя              ○ Отметить
─────────────────────────
```

Основное действие тренера:

**«Пришёл»**

При его нажатии система:

```text
1. фиксирует фактическое присутствие;
2. находит подходящий абонемент;
3. списывает одно занятие;
4. обновляет остаток.
```

Все операции выполняются в одной транзакции БД.

# 7. Администратор школы

Администратор имеет доступ к Django Admin и специализированным отчётам.

Он может управлять:

- участниками;
- аккаунтами;
- тренерами;
- группами;
- площадками;
- расписанием;
- типами занятий;
- абонементами;
- тарифами;
- фактической посещаемостью;
- корректировками списаний.

Также администратор видит ситуации, требующие внимания:

```text
Участник пришёл, но активного абонемента нет.

Абонемент закончился.

Абонемент просрочен.

Занятие отмечено задним числом.

Списание было отменено.

Остаток скорректирован вручную.
```

# 8. Типы занятий

В первой версии поддерживаются три основных типа:

```text
ICE
Лёд

CHOREOGRAPHY
Хореография

CONDITIONING
Физическая подготовка / ОФП
```

Типы рекомендуется хранить в отдельной сущности `LessonType`, а не жёстко кодировать в приложении.

Это позволит позже добавить:

- растяжку;
- прыжковую подготовку;
- индивидуальные занятия;
- сборы;
- мастер-классы.

---

# 9. Группы

Пример:

```text
Начальная 1
Начальная 2
Спортивная
Подготовительная
Взрослые
```

Участник может одновременно состоять в нескольких группах.

Связь:

```text
Participant
      │
      ▼
GroupMembership
      │
      ▼
Group
```

`GroupMembership` содержит:

- дату начала;
- дату окончания;
- признак активности.

Историческая принадлежность к группам не должна теряться.

# 10. Расписание

## 10.1. Шаблон расписания

Для регулярных занятий создаётся `ScheduleTemplate`.

Например:

```text
Группа: Начальная 1
Тип: Лёд
Тренер: Анна
День недели: Вторник
Начало: 18:00
Продолжительность: 60 минут
Площадка: Ледовый дворец
```

На основании шаблона создаются конкретные занятия.

---

# 11. Конкретное занятие

Каждое фактическое занятие — отдельный объект `Lesson`.

Например:

```text
Lesson #8172

22.09.2026
18:00–19:00

Лёд
Начальная 1
Анна
```

Именно с `Lesson` связываются:

- RSVP;
- Attendance;
- списания абонемента.

Это позволяет изменить одно занятие, не затрагивая остальные.

Например:

```text
22 сентября:
18:00 → 19:00
```

не изменяет занятия 29 сентября и 6 октября.

---

# 12. Статусы занятия

Рекомендуемые статусы:

```text
SCHEDULED
Запланировано

CANCELLED
Отменено

COMPLETED
Проведено
```

Дополнительно можно предусмотреть:

```text
RESCHEDULED
Перенесено
```

но технически перенос можно представить как изменение времени занятия с сохранением журнала изменений.

Отменённое занятие не должно расходовать абонементы.

---

# 13. RSVP

Модель:

`LessonResponse`

Ключевые поля:

```text
id
lesson_id
participant_id

status:
    YES
    NO

updated_at
updated_by
```

Отсутствие записи означает:

```text
NO_RESPONSE
```

В БД должна существовать уникальность:

```text
lesson + participant
```

---

# 14. Фактическая посещаемость

Модель:

`Attendance`

Поля:

```text
id
lesson_id
participant_id

status:
    PRESENT
    ABSENT

marked_at
marked_by
```

До выставления отметки запись может отсутствовать.

Уникальность:

```text
lesson + participant
```

---

# 15. Ключевое правило списания

**Одно посещение = одно списание из абонемента**, если тарифом явно не установлено иное.

Списание происходит только при:

```text
Attendance.status = PRESENT
```

RSVP на списание не влияет.

---

# 16. Абонементы и тарифные права

`Subscription` представляет один купленный план и может содержать независимые лимиты ICE/HALL. Срок действия определяется выбранной общешкольной моделью расчётного периода. Разовые, пробные, индивидуальные и мини-групповые занятия представлены отдельными one-time entitlements.

---

# 17. Текущая тарифная матрица

| План | ICE | HALL |
|---|---:|---:|
| 4 зала | 0 | 4 |
| 8 льдов | 8 | 0 |
| 8 льдов + 8 залов | 8 | 8 |
| 8 льдов + 12 залов | 8 | 12 |
| 12 льдов | 12 | 0 |
| 12 льдов + 8 залов | 12 | 8 |
| 12 льдов + 12 залов | 12 | 12 |
| 12 льдов + 16 залов | 12 | 16 |
| 16 льдов + 16 залов | 16 | 16 |
| 20 льдов + 16 залов | 20 | 16 |
| 20 льдов + 20 залов | 20 | 20 |
| 20 льдов + 24 зала | 20 | 24 |
| 24 льда + 24 зала | 24 | 24 |

Тарифная матрица количества ICE/HALL не определяет модель срока действия.

Школа должна поддерживать три общих модели расчётного периода:

- календарный месяц;
- 28 дней с даты первого фактически посещённого занятия;
- 28 дней с фиксированной общей датой начала для всех учеников соответствующего периода.

Конкретный Subscription фиксирует выбранную period policy snapshot-данными.

---

# 18. SubscriptionPlan и allowances

`SubscriptionPlan` содержит 1–2 `SubscriptionPlanAllowance(category, visit_limit)`. При выдаче они snapshot-копируются в `SubscriptionAllowance` конкретного Subscription.

---

# 19. Срок действия

Конкретный Subscription после активации хранит явные `valid_from/valid_until`.
Для `FIRST_ATTENDANCE_28_DAYS` даты определяются при первом покрытом
`Attendance=PRESENT`; до этого Subscription ожидает активации. Для
`FIXED_28_DAYS` даты берутся из общего школьного расчётного периода, а не
вводятся независимо для каждого ученика. Для календарной модели границы
совпадают с календарным месяцем.

Исторические даты и period policy не пересчитываются после активации.

---

# 20. Категории занятий

`ICE` покрывает лёд. `HALL` покрывает ОФП и хореографию. Смешанный план хранит оба лимита независимо.

---

# 21. Остаток

Остаток считается по каждому `SubscriptionAllowance` как сумма immutable ledger entries. Общего остатка смешанного Subscription нет.

---

# 22. Журнал операций

Ledger types: `GRANT`, `CONSUME`, `RESTORE`, `ADJUSTMENT`; каждая запись относится к конкретному allowance.

---

# 23. OneTimeEntitlement

Поддерживаются `SINGLE_ICE`, `SINGLE_HALL`, `INDIVIDUAL_ICE`, `MINI_GROUP_ICE`, `TRIAL_ICE`. Пробного HALL нет. One-time entitlement привязан к конкретному Lesson и имеет приоритет над monthly allowance.

---

# 24. AttendanceCoverage

Coverage связывает `Attendance=PRESENT` с `SubscriptionAllowance` либо `OneTimeEntitlement`; при медицинском/административном переносе дополнительно указывает `MakeupEntitlement`.

---

# 25. Выбор покрытия

Порядок: exact one-time → target makeup → other makeup → ordinary allowance (earliest expiry) → uncovered.

---

# 26. Важное правило даты

Обычный allowance проверяется относительно даты Lesson. Makeup может расширить допустимый срок конкретного source allowance.

---

# 27. Отсутствие покрытия

Отсутствие entitlement не мешает тренеру отметить реальное `PRESENT`; запись попадает в uncovered report.

---

# 28. Исправление ошибки тренера

`PRESENT → ABSENT` обращает именно активный Coverage: allowance-backed создаёт `RESTORE +1`, one-time освобождает entitlement, makeup снова становится доступным.

---

# 29. Защита от двойного списания

Один Attendance имеет не более одного активного Coverage. Ledger writer блокирует конкретный `SubscriptionAllowance`, поэтому баланс категории не может уйти ниже нуля при конкурентных отметках.

---

# 30. Отмена занятия

Если занятие отменено:

```text
Lesson.status = CANCELLED
```

оно:

- не должно отображаться как обычное предстоящее занятие;
- не должно расходовать абонементы;
- должно отображаться пользователю как отменённое.

Если по ошибке посещения уже были отмечены, система должна потребовать их обработки или автоматически сформировать возвраты.

---

# 31. No-show

В базовой версии:

```text
ответил «Буду»
        +
не пришёл
        =
занятие НЕ списывается.
```

То есть оплачивается/расходуется только фактическое посещение.

В будущем `SubscriptionPlan` можно расширить политикой:

```text
no_show_policy
```

например:

- не списывать;
- списывать при отмене позже определённого времени;
- списывать всегда.

Но это не требуется для MVP.

# 33. Экран абонемента пользователя

Для смешанного плана UI показывает независимые остатки:

```text
12 ICE + 16 HALL
Действует: 01.09–30.09

Лёд:  использовано 8, осталось 4
Зал:  использовано 10, осталось 6
```

Отдельно могут отображаться доступные one-time и makeup entitlements.

Реализованный student account доступен по `/account/`. Он показывает:

- все абонементы ученика со статусом, сроком и отдельными остатками ICE/HALL;
- one-time entitlements со статусом доступности/использования/отмены;
- makeup entitlements со сроком действия и текущей usable-семантикой;
- историю фактической посещаемости с источником active coverage;
- переключение между учениками, доступными текущему User через активный
  `StudentAccess`.

История посещений пагинируется. Деактивированный Student сохраняет доступ к
историческому account при активном `StudentAccess`, но не доступен для
schedule/RSVP.

# 37. Массовая отметка

Для ускорения работы необходимо предусмотреть:

```text
[ Отметить всех ожидаемых как пришедших ]
```

после чего тренер снимает отметки с отсутствующих.

Однако массовое действие обязательно должно требовать подтверждения:

```text
Отметить 12 человек как присутствовавших?
```

# 37.1. Mobile-first UI и адаптивность

Интерфейс пользователя и особенно интерфейс тренера проектируются по принципу **mobile-first**.

Основной рабочий сценарий тренера предполагает использование смартфона непосредственно во время занятия. Поэтому мобильная версия является основным представлением для экрана расписания и отметки посещаемости, а tablet/desktop layout — более плотной адаптацией того же интерфейса.

## Общие требования

Presentation layer не должен содержать отдельную бизнес-логику.

Любое действие UI вызывает существующий application service:

```text
RSVP
    → scheduling.services.set_lesson_response()

Attendance
    → attendance.services.set_attendance()

Массовая отметка ожидаемых
    → attendance.services.mark_expected_present()

Оставшиеся отсутствуют
    → attendance.services.mark_remaining_absent()

Завершение занятия
    → scheduling.services.complete_lesson()

Закрытие ведомости
    → attendance.services.submit_attendance()
```

Responsive layout меняет только представление данных и расположение controls. Правила доступа, допустимые state transitions, coverage и ledger semantics от размера экрана не зависят.

## Поддерживаемая ширина

Основной контент должен оставаться пригодным для работы без горизонтальной прокрутки начиная ориентировочно с:

```text
320 CSS px
```

Горизонтальная прокрутка не должна быть необходима для обычных действий:

- RSVP;
- PRESENT / ABSENT;
- открытия занятия;
- массовой отметки;
- закрытия ведомости;
- переключения ученика;
- выбора даты.

Допускается изменение конкретных CSS breakpoints без изменения этого поведенческого требования.

## Экран Attendance тренера

На мобильном экране **не используется широкая таблица**, требующая горизонтальной прокрутки.

Один Student отображается отдельной карточкой:

```text
Маша                         RSVP +

Пришёл · Покрыто

[ ✓ Пришёл ]     [ Не пришёл ]
```

До отметки:

```text
Маша                         RSVP ?

Не отмечен

[ ✓ Пришёл ]     [ Не пришёл ]
```

Карточка должна содержать:

- `Student.display_name`;
- текущий RSVP: `+ / − / ?`;
- текущий Attendance: PRESENT / ABSENT / UNMARKED;
- оперативный coverage status;
- крупные кнопки изменения Attendance.

Текущий выбранный Attendance должен быть заметен визуально, но цвет не должен быть единственным способом передачи состояния: сохраняется текстовая подпись.

## Coverage на экране тренера

Тренер видит только необходимый оперативный статус.

Допустимые примеры:

```text
Покрыто
Без покрытия
5/8
```

Не показываются:

- цена;
- платежи;
- возвраты;
- финансовая история;
- внутренние ledger entries;
- административные комментарии.

Если в дальнейшем отображается остаток вида `5/8`, он вычисляется из entitlement/allowance read-side и не хранится отдельным mutable полем в Attendance.

## Массовые действия

На мобильном экране массовые действия должны оставаться доступными при длинном roster.

Рекомендуемое представление — нижняя sticky action panel:

Верхняя навигация может оставаться sticky.

- последнюю карточку ученика;
- browser/system safe area;
- сообщения об ошибках;
- submit controls.

## Формы и ввод

Select, date input и login controls должны занимать доступную ширину на узком экране.

Основные формы не должны требовать pinch zoom.

Размер текста input должен оставаться достаточным, чтобы мобильные браузеры не выполняли нежелательный auto-zoom при фокусе.

## Состояния и обратная связь

После POST пользователь должен получить однозначную обратную связь:

- новое состояние визуально отображается после redirect;
- ValidationError показывается через messages framework;
- успешные массовые операции могут показывать число изменённых записей;
- отсутствие Coverage не блокирует PRESENT и отображается как `Без покрытия`.

PRG pattern:

```text
POST
  ↓
application service
  ↓
redirect
  ↓
GET с актуальным состоянием
```

предпочтителен для всех пользовательских действий.

## Accessibility baseline

Минимальные требования:

- controls доступны с клавиатуры;
- интерактивные элементы имеют заметный focus state;

# 52. Авторизация сотрудников

Привилегированные web-аккаунты используют отдельный local password + MFA.
MFA обязательна для:

- `is_staff`;
- `is_superuser`;
- User с любым manager-operation permission, в том числе выданным через Group.

Для этих аккаунтов внешний вход через Яндекс/VK запрещён.

Поддерживаемый второй фактор текущей версии:

```text
TOTP authenticator
```

SMS/email OTP не используются. После первого успешного ввода пароля User
обязан подтвердить TOTP enrollment; до этого полноценная authenticated session
не создаётся. Password-only pre-auth state имеет короткий TTL.

При enrollment выдаются 10 одноразовых recovery codes. Каждый код удаляется
после успешного использования. Recovery code является аварийным вторым
фактором, а не заменой постоянного TOTP.

Уже существующая privileged session без OTP verification не даёт доступа к
manager/staff/admin UI. Такая session завершается, после чего User обязан
заново ввести local password и пройти TOTP/recovery challenge. Это
распространяется и на Django Admin.

После успешной MFA-проверки в server-side session фиксируется timestamp
verification. Privileged session имеет **абсолютный** maximum age 12 часов по
умолчанию (configurable): активность и другие изменения session не сдвигают
этот предел. После истечения требуется новый local password + MFA.

В web UI пользователь может:

- увидеть количество оставшихся recovery codes;
- перевыпустить recovery codes;
- заменить приложение-аутентификатор.

Обе self-service операции требуют уже MFA-verified session и повторный ввод
текущего локального пароля.

Для аварийного server-side восстановления допускается management command
`addstatictoken`. Если у User после такого входа отсутствует confirmed TOTP,
система принудительно переводит его в новый TOTP enrollment.

При увольнении/компрометации локальный privileged User должен быть
деактивирован; удаление/смена MFA не заменяет блокировку самого аккаунта.

Обычный тренер без staff/manager permissions может продолжать использовать
внешнюю авторизацию согласно организационной модели.

# 57. Развёртывание

Минимальный production deployment — один Docker Compose host:

```text
Internet
   │
   ▼
Caddy :80/:443
   │
   ▼
Gunicorn / Django
   │
   ▼
PostgreSQL

sidecars:
scheduler
backup
```

Production compose обязан обеспечивать следующие свойства:

- PostgreSQL не публикует порт наружу;
- Gunicorn доступен только во внутренней Compose-сети;
- публичный вход идёт только через Caddy;
- миграции выполняются отдельным one-shot service до запуска web/scheduler;
- Caddy начинает проксировать только после успешного healthcheck web;
- scheduler и backup используют ту же production БД, но не обслуживают HTTP;
- Docker stdout/stderr logs каждого service имеют bounded local rotation, чтобы
  unattended host не заполнял диск неограниченным `json-file` log.

Reverse proxy обязан **перезаписывать** `X-Real-IP` реальным адресом прямого
клиента. Приложение доверяет этому заголовку только когда непосредственный
`REMOTE_ADDR` входит в `TRUSTED_PROXY_IPS`.

В поставляемом Compose Caddy имеет фиксированный внутренний IP
`172.30.0.10`, который и указывается в `TRUSTED_PROXY_IPS`.
Если production host не может использовать subnet `172.30.0.0/24`, subnet,
proxy IP и `TRUSTED_PROXY_IPS` меняются согласованно.

Приложение не использует `X-Forwarded-For` для Axes rate limiting.

Static assets собираются в application image через `collectstatic` и
обслуживаются WhiteNoise. Writable shared static volume между proxy и web не
требуется.

Proxy access logs не должны сохранять bearer/one-time secrets. Маршруты
invitation/recovery token, OAuth callback с authorization code/state и Django
password-reset token исключаются из Caddy access logging; остальные proxy
access logs сохраняются с bounded Docker rotation.
Gunicorn access log отключён, чтобы второй слой HTTP logging не обходил эти
exclusions; Gunicorn error log остаётся включённым.

Healthcheck web проверяет одновременно Gunicorn и доступность PostgreSQL через
`/healthz/`. Внутренний probe передаёт production Host и
`X-Forwarded-Proto=https`, поэтому не требует ослаблять `ALLOWED_HOSTS` или
`SECURE_SSL_REDIRECT`.

Docker health status является локальным сигналом и сам по себе не является
restart/alerting mechanism. Production deployment должен иметь внешний HTTPS
uptime check для `/healthz/` и dead-man monitoring для scheduler jobs и
backup. Success-ping URLs хранятся как production secrets и не логируются.

Redis/Celery для первой production версии не обязательны.

Их можно добавить позже для:

- фоновых задач, которым нужна очередь;
- уведомлений;
- тяжёлой asynchronous обработки;
- distributed scheduler/worker topology;
- кеширования.

# 58. Резервное копирование

Production backup sidecar использует `pg_dump --format=custom` той же major
версии PostgreSQL, что и сервер.

Минимальные инварианты backup:

1. backup запускается сразу при старте контейнера и далее с настраиваемым
   интервалом;
2. dump сначала пишется во временный `.partial`;
3. `pg_dump` ограничен `BACKUP_TIMEOUT_SECONDS`; timeout завершает зависший
   процесс, удаляет `.partial` и оставляет run неуспешным для последующего retry;
4. после `pg_dump` archive проверяется через `pg_restore --list`;
5. только успешно проверенный archive атомарно переименовывается в `.dump`;
6. backup files создаются с `umask 077`;
7. старые dumps удаляются по configurable retention policy;
8. manual `--once` backup доступен оператору без остановки основного loop.

Значения первой версии:

```text
BACKUP_INTERVAL_SECONDS = 86400
BACKUP_TIMEOUT_SECONDS  = 3600
BACKUP_RETENTION_DAYS    = 14
```

Успешный backup обновляет local last-success marker только после
`pg_restore --list`. При настроенном `BACKUP_SUCCESS_PING_URL` после этого
отправляется optional dead-man success ping. Ошибка доставки monitoring ping
не должна инвалидировать уже проверенный dump.

Локальный backup directory **не считается достаточной стратегией**.
Проверенные dumps должны копироваться в защищённое off-host storage согласно
операционной политике организации.

Восстановление выполняется только после остановки writers
(`proxy/web/scheduler/backup`). Restore должен использовать
`pg_restore --clean --if-exists --no-owner --no-privileges`, после чего
применяются миграции текущего application image и выполняются smoke checks
health/login/schedule/audit/subscription state.

Restore procedure необходимо регулярно тестировать. Наличие dump-файла без
проверенного restore не считается подтверждённой резервной копией. CI должен
как минимум восстанавливать созданный custom-format dump во временную
PostgreSQL database и проверять доступность Django migration metadata; это
smoke-проверка формата/restore path, а не замена периодического recovery drill.

Секреты приложения не должны храниться внутри database dump; production env и
другие secrets резервируются отдельным защищённым процессом.

# 59. Генерация занятий и scheduler

Recurring operational jobs выполняются отдельным single-replica scheduler
process без Celery/Redis.

Первая версия запускает:

```text
process_subscription_lifecycle
    default interval = 3600 s

generate_lessons --all-active --horizon-days 60
    default interval = 21600 s
```

Оба job запускаются сразу после старта scheduler, затем повторяются независимо.

Настройки:

```text
SCHEDULER_LIFECYCLE_INTERVAL_SECONDS
SCHEDULER_GENERATION_INTERVAL_SECONDS
SCHEDULER_GENERATION_HORIZON_DAYS
SCHEDULER_LIFECYCLE_TIMEOUT_SECONDS
SCHEDULER_GENERATION_TIMEOUT_SECONDS
SCHEDULER_LIFECYCLE_SUCCESS_PING_URL
SCHEDULER_GENERATION_SUCCESS_PING_URL
```

Scheduler использует monotonic clock для interval scheduling и не запускает
новый экземпляр одного job параллельно предыдущему в рамках одного process.
Jobs выполняются последовательно, поэтому каждый management command имеет
hard timeout. Lifecycle timeout по умолчанию равен lifecycle interval;
generation timeout по умолчанию ограничен меньшим из generation interval и
lifecycle interval. Timeout принудительно завершает management command,
логируется как `event=timeout` и не обновляет success marker/ping.

Неуспешный management command:

- пишет exit code в stdout/stderr operational log;
- не завершает scheduler process;
- повторяется при следующем scheduled interval.

Успешное выполнение каждого job обновляет отдельный last-success marker и,
если настроен соответствующий URL, отправляет dead-man success ping.
Monitoring delivery failure логируется отдельно и не меняет локальный статус
успешно завершённого domain job. Container healthcheck проверяет freshness
обоих markers относительно `2 * interval + grace`. Поэтому повторяющиеся
failures/timeouts становятся видны как unhealthy deployment state, не
останавливая scheduler process принудительным restart.

Это особенно важно для `generate_lessons`: unresolved generation conflict
должен оставаться заметной ошибкой конкретного запуска, но не должен
останавливать lifecycle processing.

Scheduler не масштабируется более чем до одной replica. Management commands
остаются идемпотентными как дополнительная защита, но duplicate scheduler
replicas считаются ошибкой deployment topology.

Горизонт генерации по умолчанию — 60 дней.

Scheduler первой версии **не** автоматизирует `publish_daily_schedule`,
evaluation у decision deadline и перевод проведённых занятий в `COMPLETED`.
Эти действия остаются ежедневными web-first операциями менеджера/тренера.
Будущая автоматизация должна добавляться как отдельные явно включённые и
независимо monitored jobs после фиксации timing и audit/actor semantics.

Команда генерации должна быть идемпотентной:

повторный запуск не создаёт дубликаты.


# 60. Изменение шаблона

Изменение:

```text
каждый вторник 18:00
```

не должно автоматически переписывать уже проведённые занятия.

ScheduleTemplate не редактируется in-place после начала использования.
Изменение создаёт новую версию шаблона с `valid_from = effective_from`, а
старую версию ограничивает `valid_until = effective_from - 1`, оставляя её
генерируемой до конца собственного интервала.

Versioning запрещается, если на `effective_from` и позже у старого шаблона
есть опубликованные/подтверждённые/завершённые занятия либо DRAFT с активным
LessonEnrollment или OneTimeEntitlement. Забронированный DRAFT нужно сначала
явно перенести через `reschedule_lesson`: DRAFT-reschedule разрешён и
cross-app workflow переносит активные LessonEnrollment и неиспользованные
OneTimeEntitlement на replacement. Replacement можно поставить сразу в будущий регулярный слот новой версии.

При генерации пересекающееся неотменённое занятие той же группы считается
покрытием регулярного слота **только если совпадает LessonType**. Если тип
отличается, генератор не пропускает регулярное занятие молча: записывается
`LessonGenerationConflict`, а management command завершает запуск ошибкой,
чтобы cron/monitoring заметили конфликт.

Если concrete Lesson самого ScheduleTemplate на этот `starts_at` уже
существует в любом статусе, включая CANCELLED, он считается явным решением
школы по этому слоту и проверка внешних пересечений для него не выполняется.
Повторный unresolved конфликт продолжает завершать cron ошибкой, но одинаковый
audit event для `template + expected_starts_at` не дублируется.

Только безопасные будущие DRAFT без броней автоматически переводятся в
CANCELLED.

# 66. Критические бизнес-инварианты

1. Один Attendance на Student+Lesson.
2. Один active AttendanceCoverage на Attendance.
3. RSVP не расходует entitlement.
4. ICE и HALL balances независимы.
5. One-time entitlement имеет приоритет над monthly allowance для своего Lesson.
6. `PRESENT → ABSENT` обращает именно использованное покрытие.
7. Attendance может быть PRESENT без покрытия.
8. Ledger immutable; ручная корректировка — `ADJUSTMENT` allowance.
9. Makeup не увеличивает купленный лимит.
10. Отмена Lesson сама по себе не создаёт CONSUME.

# 84. Модели расчётного периода

Поддерживаются три общешкольные модели:

```text
CALENDAR_MONTH
FIRST_ATTENDANCE_28_DAYS
FIXED_28_DAYS
```

Для 28-дневной модели день начала считается первым днём, поэтому:

```text
valid_until = valid_from + 27 days
```

`FIRST_ATTENDANCE_28_DAYS` активируется только фактическим первым
`Attendance=PRESENT`, покрытым этим Subscription. RSVP не активирует
абонемент.

Если coverage активационного занятия впоследствии отменён, rolling-период
возвращается ACTIVE → PENDING только при отсутствии других active coverages и
зависимых makeup/compensation rights. При наличии зависимостей записывается
`SubscriptionPeriodActivationRevertSkipped`, а manager web показывает
причину, ссылки на разрешение blocker и действие повторного recovery.
Повторный recovery заново проверяет зависимости; успешный переход очищает
даты/activation metadata и записывает
`SubscriptionPeriodActivationReverted(reason=manager_recovery)`.

`FIXED_28_DAYS` использует общую запись расчётного периода, чтобы все ученики
имели одинаковые даты.

Подробное архитектурное направление описано в
`Абонементы — расчётные периоды, заморозка и web-операции.md`.

# 85. Компенсация пропусков и заморозка

Школа дорабатывает правила компенсации пропущенных занятий, поэтому они должны
реализовываться как versioned policy, а не как жёстко заданный перенос остатка.

Текущие известные варианты:

- болезнь со справкой → бесплатная отработка в системе; возможный денежный
  перерасчёт выполняется бухгалтерией вне приложения;
- пропуск без уважительной причины → бесплатная отработка в текущем
  расчётном периоде либо платная заморозка/отработка в последующем;
- платная заморозка по текущему правилу оплачивается вместе с Subscription
  следующего периода;
- для неуважительных пропусков первые четыре могут давать право на отработку,
  пятый и последующие — нет;
- майские пропуски могут отрабатываться в июне без покупки июньского
  Subscription;
- июньские пропуски могут отрабатываться в августе при наличии оплаченного
  августовского Subscription.

Эти значения являются policy parameters и seasonal exceptions, а не
константами приложения.

Компенсация должна быть трассируема до конкретного source Lesson /
Attendance=ABSENT и, при необходимости, source SubscriptionAllowance.
Исторический Subscription, Attendance и immutable ledger задним числом не
переписываются.

Архитектура должна позволять менять лимит, target-period rule, требования к
оплате/наличию target Subscription и сезонные исключения без изменения схемы
БД при каждом изменении правил школы.

# 86. Платное сохранение места в группе

Должна поддерживаться отдельная услуга сохранения места в TrainingGroup на один
пропущенный расчётный период.

Она:

- сохраняет место ученика в группе;
- не является Subscription;
- не создаёт ICE/HALL balance;
- не участвует в AttendanceCoverage;
- не является medical/admin makeup;
- должна быть видима и управляться менеджером через web.

Денежная часть услуги относится к внешней бухгалтерии. В приложении допустимо
административное подтверждение факта оплаты/предоставления услуги без хранения
суммы, платёжных реквизитов или алгоритма расчёта.

# 87. Web-first управление

Все штатные действия менеджера школы и тренера должны быть доступны в
аутентифицированном web-интерфейсе.

Management commands являются secondary interface для системного администратора,
cron/automation, диагностики и аварийных операций. Наличие CLI-команды не
считается достаточной реализацией manager/trainer workflow.

В частности, через web должны быть доступны resolution generation conflicts,
`skip_template_occurrence`, управление расписанием, memberships,
Subscriptions, расчётными периодами, freeze/carry-over, сохранением места,
one-time/makeup operations и релевантным audit trail. В том числе manager web
должен позволять разрешить skipped rollback rolling-периода после устранения
его зависимостей. Standalone administrative/school-reschedule makeup может
быть отменён с обязательной причиной; medical и absence-compensation права
отменяются только через свои source workflows.

Чисто фоновые jobs могут оставаться CLI/cron, но их ошибки и конфликты должны
быть видимы менеджеру в web и иметь понятное действие для разрешения.


# 88. External identity onboarding и приглашения

Вход участника, родителя и тренера через Yandex/VK реализуется по принципу
**invitation-only onboarding**.

Обычный OAuth callback неизвестной внешней identity не создаёт User. Первый
вход возможен только после одноразового приглашения менеджера. Приглашение
содержит заранее определённый school target:

- Student + роль SELF/GUARDIAN + понятная подпись аккаунта
  (например, «Мама Ани»); либо
- будущий CoachProfile + display name, который одновременно используется как
  подпись User.

Секрет приглашения хранится только в исходной ссылке; в БД сохраняется
SHA-256 hash. Приглашение имеет срок действия, может быть отозвано и после
успешного принятия становится терминальным.

После успешной внешней авторизации одна транзакция создаёт:

```text
technical User
ExternalIdentity
StudentAccess | CoachProfile
accepted AccountInvitation
```

Если ExternalIdentity уже существует, тот же User может принять новое
приглашение (например, родитель второго ребёнка), но новый User не создаётся.

OAuth-поток:

- Yandex: Authorization Code + PKCE S256 + state;
- VK ID: OAuth 2.1 Authorization Code + PKCE S256 + state + device_id;
- callback state одноразовый и ограничен по времени;
- access/refresh tokens используются только для получения provider subject и
  не сохраняются;
- дополнительные provider profile fields не сохраняются.

Для Yandex provider_subject **всегда** равен pairwise `psuid`. Если `psuid`
не возвращён, login/link завершается ошибкой; fallback на глобальный `id`
запрещён. Это исключает смену формата идентификатора одного и того же аккаунта
между входами. Для VK ID используется `user_id` из `oauth2/user_info`.

Один User может иметь не более одной ExternalIdentity каждого provider.
Привязка второго provider выполняется только из уже аутентифицированной
Django-сессии. ExternalIdentity, уже принадлежащую другому User, перепривязать
нельзя.

Если пользователь уже аутентифицирован и принимает новое приглашение, выбранная
внешняя identity сначала связывается с текущим User, а затем в той же транзакции
материализуется StudentAccess/CoachProfile. Поэтому смена Yandex → VK между
приглашениями не создаёт второй технический User. Если provider subject уже
принадлежит другому User, acceptance отклоняется без частично созданной роли
или связи.

Для invitation-flow используется единый lock-order:

```text
AccountInvitation -> User -> ExternalIdentity -> target role
```

Обычные login/link без invitation используют `User -> ExternalIdentity`.
Это правило обязательно для дальнейших identity-сервисов.

External auth запрещён для `is_staff`, `is_superuser` и любого User,
которому доступны manager operations. Это ограничение применяется одинаково к
обычному external login, привязке provider и принятию invitation из уже
аутентифицированной privileged-сессии. Для административного контура
единственным штатным способом входа остаётся локальный Django password login
с действием django-axes.

External-only User создаётся с unusable password и human-readable
`display_name` из invitation. Технический `username` не должен использоваться
как основная подпись в пользовательском или manager UI.

ExternalIdentity можно отвязать:

- сам пользователь — только если после операции остаётся другой external
  provider;
- менеджер с `change_externalidentity` — для активного User только если после
  операции остаётся другой provider либо есть usable local password;
- последний provider external-only User можно удалить после деактивации User.

Для аварийного восстановления single-provider аккаунта используется
фиксированная последовательность:

```text
deactivate existing User
    ->
unlink compromised ExternalIdentity
    ->
issue AccountInvitation(kind=RECOVERY, recovery_user=<same User>)
    ->
new Yandex/VK authentication while signed out
    ->
link identity to the same User
    ->
reactivate the same User
```

RECOVERY-invitation может быть выдан только неактивному non-privileged User,
у которого уже удалены все старые ExternalIdentity. Invitation привязан к UUID
существующего User и не создаёт новый User, StudentAccess или CoachProfile.
Поэтому прежние дети, роли, посещения и история остаются на исходном аккаунте.

При manager-unlink у external-only User дополнительно ротируется unusable
password hash: ранее выданные Django-сессии перестают проходить проверку
session auth hash. Каждая операция unlink фиксируется
`ExternalIdentityUnlinked`, а успешное восстановление — `AccountRecovered`.
