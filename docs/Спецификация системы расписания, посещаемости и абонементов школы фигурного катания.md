# Спецификация системы расписания, посещаемости и абонементов школы фигурного катания

**Версия:** 1.0  
**Стек:** Django + PostgreSQL + Django Admin + server-rendered frontend  
**Статус:** базовая спецификация MVP с возможностью дальнейшего расширения

---

# 1. Назначение системы

Система предназначена для организации расписания занятий школы фигурного катания, предварительного подтверждения участия учениками/родителями, фиксации фактической посещаемости тренерами и учёта абонементов.

Система должна заменить существующую схему, при которой расписание публикуется в чате, а участники ставят `+` или `-`.

Основные задачи:

1. Ведение групп, тренеров и расписания.
2. Публикация персонального расписания для каждого участника.
3. Возможность заранее отметить:
   - «Буду»;
   - «Не буду».
4. Отображение организатору ожидаемого количества участников.
5. Фиксация тренером фактического присутствия.
6. Учёт абонементов с ограниченным количеством занятий и сроком действия.
7. Автоматическое списание занятия из абонемента при фактическом посещении.
8. Отображение остатка абонемента.
9. Минимизация объёма персональных данных.
10. Возможность в будущем подключить оплату, не меняя основную архитектуру.

---

# 2. Основные принципы

## 2.1. Фактическое посещение отделяется от намерения прийти

В системе существуют два независимых понятия.

### RSVP

Ответ пользователя до занятия:

- буду;
- не буду;
- нет ответа.

RSVP используется для планирования количества участников.

Он **не списывает занятие из абонемента**.

### Attendance

Фактическая отметка тренера:

- присутствовал;
- отсутствовал;
- не отмечено.

Именно фактическое присутствие является основанием для расходования занятия из абонемента.

Таким образом:

```text
«Буду» → занятие не списывается.

Тренер отметил «Пришёл» → занятие списывается.
```

# 3. Архитектура

Система реализуется как единое Django-приложение.

```text
                  Пользователь
             телефон / ПК / планшет
                       │
                     HTTPS
                       │
                       ▼
              ┌─────────────────┐
              │     Django      │
              │                 │
              │ Server-rendered │
              │    frontend     │
              │                 │
              │  Business logic │
              │                 │
              │  Django Admin   │
              └────────┬────────┘
                       │
                       ▼
               ┌──────────────┐
               │ PostgreSQL   │
               └──────────────┘
```

Отдельное SPA на React/Vue в первой версии не требуется.

Frontend реализуется через:

- Django Templates;
- HTML;
- CSS;
- минимальный JavaScript;
- при необходимости HTMX.

Это уменьшает:

- количество компонентов;
- объём JavaScript;
- сложность авторизации;
- количество API;
- поверхность атаки;
- стоимость сопровождения.

# 4. Пользовательские роли

## 4.1. Участник / родитель

Может:

- войти через внешний Identity Provider;
- видеть расписание связанных с аккаунтом участников;
- переключаться между детьми, если их несколько;
- ставить «Буду» / «Не буду»;
- видеть состояние своего абонемента;
- видеть количество оставшихся занятий;
- видеть срок действия абонемента;
- видеть историю собственных посещений.

Не может:

- видеть других участников;
- видеть списки группы;
- изменять фактическую посещаемость;
- изменять абонемент.

# 5. Родитель и ребёнок

Учётная запись и занимающийся человек должны быть разными сущностями.

Например:

```text
Account
   │
   ├── Маша
   │     └── группа «Начальная 1»
   │
   └── Петя
         └── группа «Подготовительная»
```

Это позволяет использовать один аккаунт родителя для нескольких детей.

Отдельная учётная запись ребёнку не требуется.

Также допускается:

```text
Account → Participant
```

когда совершеннолетний участник самостоятельно пользуется системой.

---

# 6. Тренер

Тренер должен иметь специализированный интерфейс, не требующий работы непосредственно с Django Admin.

Тренер может:

- видеть сегодняшние занятия;
- видеть назначенные ему занятия;
- видеть участников соответствующей группы;
- видеть RSVP;
- отмечать фактическое присутствие;
- исправлять ошибочно поставленную отметку в пределах разрешённого периода.

Например:

```text
Лёд
14 сентября
17:00–18:00

Ожидалось: 12

─────────────────────────
Маша             ✓ Пришла
Катя              ✓ Пришла
Саша              ○ Отметить
Ира               ✕ Нет
Петя              ○ Отметить
─────────────────────────
```

Основное действие тренера:

**«Пришёл»**

При его нажатии система:

```text
1. фиксирует фактическое присутствие;
2. находит подходящий абонемент;
3. списывает одно занятие;
4. обновляет остаток.
```

Все операции выполняются в одной транзакции БД.

# 7. Администратор школы

Администратор имеет доступ к Django Admin и специализированным отчётам.

Он может управлять:

- участниками;
- аккаунтами;
- тренерами;
- группами;
- площадками;
- расписанием;
- типами занятий;
- абонементами;
- тарифами;
- фактической посещаемостью;
- корректировками списаний.

Также администратор видит ситуации, требующие внимания:

```text
Участник пришёл, но активного абонемента нет.

Абонемент закончился.

Абонемент просрочен.

Занятие отмечено задним числом.

Списание было отменено.

Остаток скорректирован вручную.
```

# 8. Типы занятий

В первой версии поддерживаются три основных типа:

```text
ICE
Лёд

CHOREOGRAPHY
Хореография

CONDITIONING
Физическая подготовка / ОФП
```

Типы рекомендуется хранить в отдельной сущности `LessonType`, а не жёстко кодировать в приложении.

Это позволит позже добавить:

- растяжку;
- прыжковую подготовку;
- индивидуальные занятия;
- сборы;
- мастер-классы.

---

# 9. Группы

Пример:

```text
Начальная 1
Начальная 2
Спортивная
Подготовительная
Взрослые
```

Участник может одновременно состоять в нескольких группах.

Связь:

```text
Participant
      │
      ▼
GroupMembership
      │
      ▼
Group
```

`GroupMembership` содержит:

- дату начала;
- дату окончания;
- признак активности.

Историческая принадлежность к группам не должна теряться.

# 10. Расписание

## 10.1. Шаблон расписания

Для регулярных занятий создаётся `ScheduleTemplate`.

Например:

```text
Группа: Начальная 1
Тип: Лёд
Тренер: Анна
День недели: Вторник
Начало: 18:00
Продолжительность: 60 минут
Площадка: Ледовый дворец
```

На основании шаблона создаются конкретные занятия.

---

# 11. Конкретное занятие

Каждое фактическое занятие — отдельный объект `Lesson`.

Например:

```text
Lesson #8172

22.09.2026
18:00–19:00

Лёд
Начальная 1
Анна
```

Именно с `Lesson` связываются:

- RSVP;
- Attendance;
- списания абонемента.

Это позволяет изменить одно занятие, не затрагивая остальные.

Например:

```text
22 сентября:
18:00 → 19:00
```

не изменяет занятия 29 сентября и 6 октября.

---

# 12. Статусы занятия

Рекомендуемые статусы:

```text
SCHEDULED
Запланировано

CANCELLED
Отменено

COMPLETED
Проведено
```

Дополнительно можно предусмотреть:

```text
RESCHEDULED
Перенесено
```

но технически перенос можно представить как изменение времени занятия с сохранением журнала изменений.

Отменённое занятие не должно расходовать абонементы.

---

# 13. RSVP

Модель:

`LessonResponse`

Ключевые поля:

```text
id
lesson_id
participant_id

status:
    YES
    NO

updated_at
updated_by
```

Отсутствие записи означает:

```text
NO_RESPONSE
```

В БД должна существовать уникальность:

```text
lesson + participant
```

---

# 14. Фактическая посещаемость

Модель:

`Attendance`

Поля:

```text
id
lesson_id
participant_id

status:
    PRESENT
    ABSENT

marked_at
marked_by
```

До выставления отметки запись может отсутствовать.

Уникальность:

```text
lesson + participant
```

---

# 15. Ключевое правило списания

**Одно посещение = одно списание из абонемента**, если тарифом явно не установлено иное.

Списание происходит только при:

```text
Attendance.status = PRESENT
```

RSVP на списание не влияет.

---

# 16. Абонементы и тарифные права

Месячный `Subscription` представляет один купленный план и может содержать независимые лимиты ICE/HALL. Разовые, пробные, индивидуальные и мини-групповые занятия представлены отдельными one-time entitlements.

---

# 17. Текущая тарифная матрица

| План | ICE | HALL |
|---|---:|---:|
| 4 зала | 0 | 4 |
| 8 льдов | 8 | 0 |
| 8 льдов + 8 залов | 8 | 8 |
| 8 льдов + 12 залов | 8 | 12 |
| 12 льдов | 12 | 0 |
| 12 льдов + 8 залов | 12 | 8 |
| 12 льдов + 12 залов | 12 | 12 |
| 12 льдов + 16 залов | 12 | 16 |
| 16 льдов + 16 залов | 16 | 16 |
| 20 льдов + 16 залов | 20 | 16 |
| 20 льдов + 20 залов | 20 | 20 |
| 20 льдов + 24 зала | 20 | 24 |
| 24 льда + 24 зала | 24 | 24 |

Все текущие планы действуют один месяц.

---

# 18. SubscriptionPlan и allowances

`SubscriptionPlan` содержит 1–2 `SubscriptionPlanAllowance(category, visit_limit)`. При выдаче они snapshot-копируются в `SubscriptionAllowance` конкретного Subscription.

---

# 19. Срок действия

Конкретный Subscription хранит явные `valid_from/valid_until`. Business policy определяет, как рассчитывается один месяц; исторические даты не пересчитываются.

---

# 20. Категории занятий

`ICE` покрывает лёд. `HALL` покрывает ОФП и хореографию. Смешанный план хранит оба лимита независимо.

---

# 21. Остаток

Остаток считается по каждому `SubscriptionAllowance` как сумма immutable ledger entries. Общего остатка смешанного Subscription нет.

---

# 22. Журнал операций

Ledger types: `GRANT`, `CONSUME`, `RESTORE`, `ADJUSTMENT`; каждая запись относится к конкретному allowance.

---

# 23. OneTimeEntitlement

Поддерживаются `SINGLE_ICE`, `SINGLE_HALL`, `INDIVIDUAL_ICE`, `MINI_GROUP_ICE`, `TRIAL_ICE`. Пробного HALL нет. One-time entitlement привязан к конкретному Lesson и имеет приоритет над monthly allowance.

---

# 24. AttendanceCoverage

Coverage связывает `Attendance=PRESENT` с `SubscriptionAllowance` либо `OneTimeEntitlement`; при медицинском/административном переносе дополнительно указывает `MakeupEntitlement`.

---

# 25. Выбор покрытия

Порядок: exact one-time → target makeup → other makeup → ordinary allowance (earliest expiry) → uncovered.

---

# 26. Важное правило даты

Обычный allowance проверяется относительно даты Lesson. Makeup может расширить допустимый срок конкретного source allowance.

---

# 27. Отсутствие покрытия

Отсутствие entitlement не мешает тренеру отметить реальное `PRESENT`; запись попадает в uncovered report.

---

# 28. Исправление ошибки тренера

`PRESENT → ABSENT` обращает именно активный Coverage: allowance-backed создаёт `RESTORE +1`, one-time освобождает entitlement, makeup снова становится доступным.

---

# 29. Защита от двойного списания

Один Attendance имеет не более одного активного Coverage. Ledger writer блокирует конкретный `SubscriptionAllowance`, поэтому баланс категории не может уйти ниже нуля при конкурентных отметках.

---

# 30. Отмена занятия

Если занятие отменено:

```text
Lesson.status = CANCELLED
```

оно:

- не должно отображаться как обычное предстоящее занятие;
- не должно расходовать абонементы;
- должно отображаться пользователю как отменённое.

Если по ошибке посещения уже были отмечены, система должна потребовать их обработки или автоматически сформировать возвраты.

---

# 31. No-show

В базовой версии:

```text
ответил «Буду»
        +
не пришёл
        =
занятие НЕ списывается.
```

То есть оплачивается/расходуется только фактическое посещение.

В будущем `SubscriptionPlan` можно расширить политикой:

```text
no_show_policy
```

например:

- не списывать;
- списывать при отмене позже определённого времени;
- списывать всегда.

Но это не требуется для MVP.

# 37. Массовая отметка

Для ускорения работы необходимо предусмотреть:


после чего тренер снимает отметки с отсутствующих.

# 37.1. Mobile-first UI и адаптивность

Интерфейс пользователя и особенно интерфейс тренера проектируются по принципу **mobile-first**.

Основной рабочий сценарий тренера предполагает использование смартфона непосредственно во время занятия. Поэтому мобильная версия является основным представлением для экрана расписания и отметки посещаемости, а tablet/desktop layout — более плотной адаптацией того же интерфейса.

## Общие требования

Presentation layer не должен содержать отдельную бизнес-логику.

Любое действие UI вызывает существующий application service:

```text
RSVP
    → scheduling.services.set_lesson_response()

Attendance
    → attendance.services.set_attendance()

Массовая отметка ожидаемых
    → attendance.services.mark_expected_present()

Оставшиеся отсутствуют
    → attendance.services.mark_remaining_absent()

Завершение занятия
    → scheduling.services.complete_lesson()

Закрытие ведомости
    → attendance.services.submit_attendance()
```

Responsive layout меняет только представление данных и расположение controls. Правила доступа, допустимые state transitions, coverage и ledger semantics от размера экрана не зависят.

## Поддерживаемая ширина

Основной контент должен оставаться пригодным для работы без горизонтальной прокрутки начиная ориентировочно с:

```text
320 CSS px
```

Горизонтальная прокрутка не должна быть необходима для обычных действий:

- RSVP;
- PRESENT / ABSENT;
- открытия занятия;
- массовой отметки;
- закрытия ведомости;
- переключения ученика;
- выбора даты.

Допускается изменение конкретных CSS breakpoints без изменения этого поведенческого требования.

Текущая reference implementation использует переход к более плотной desktop-компоновке примерно от:

```text
720 px
```

## Touch targets

Интерактивные элементы должны быть удобны для управления пальцем.

Минимальный практический touch target:

```text
44 × 44 CSS px
```

Для основных кнопок рабочего процесса рекомендуется:

```text
минимальная высота 48 px
```

К основным touch controls относятся:

- `+ Буду`;
- `− Не буду`;
- `Пришёл`;
- `Не пришёл`;
- массовые действия тренера;
- `Закрыть ведомость`;
- переключатель ученика;
- выбор даты.

Нельзя требовать точного попадания в маленькую иконку, checkbox или текстовую ссылку для основного действия Attendance.

## Экран ученика / родителя

Расписание отображается карточками занятий.

Мобильное представление одной карточки:

```text
15.09 · 17:00–18:00        Буду

Лёд
Анна · Ледовый дворец

[ ✓ Буду ]        [ Не буду ]
```

Если Attendance уже существует, карточка дополнительно показывает фактический статус:

```text
Пришёл · Покрыто
```

или:

```text
Пришёл · Без покрытия
```

или:

```text
Отсутствовал
```

Если Lesson отменён, отмена должна быть заметна без перехода на отдельную страницу.

При наличии доступа к нескольким Student переключение ученика остаётся доступным на мобильном экране и определяет весь отображаемый student context.

## Расписание тренера

Список занятий тренера отображается карточками.

Для каждого Lesson показываются как минимум:

```text
время
lesson type
group
venue

YES count
NO count
NO RESPONSE count

[ Открыть занятие ]
```

На узком экране карточки располагаются в одну колонку.

На tablet/desktop допускается несколько колонок, если это не ухудшает читаемость и touch-доступность.

## Экран Attendance тренера

На мобильном экране **не используется широкая таблица**, требующая горизонтальной прокрутки.

Один Student отображается отдельной карточкой:

```text
Маша                         RSVP +

Пришёл · Покрыто

[ ✓ Пришёл ]     [ Не пришёл ]
```

До отметки:

```text
Маша                         RSVP ?

Не отмечен

[ ✓ Пришёл ]     [ Не пришёл ]
```

Карточка должна содержать:

- `Student.display_name`;
- текущий RSVP: `+ / − / ?`;
- текущий Attendance: PRESENT / ABSENT / UNMARKED;
- оперативный coverage status;
- крупные кнопки изменения Attendance.

Текущий выбранный Attendance должен быть заметен визуально, но цвет не должен быть единственным способом передачи состояния: сохраняется текстовая подпись.

## Coverage на экране тренера

Тренер видит только необходимый оперативный статус.

Допустимые примеры:

```text
Покрыто
Без покрытия
5/8
```

Не показываются:

- цена;
- платежи;
- возвраты;
- финансовая история;
- внутренние ledger entries;
- административные комментарии.

Если в дальнейшем отображается остаток вида `5/8`, он вычисляется из entitlement/allowance read-side и не хранится отдельным mutable полем в Attendance.

## Массовые действия

На мобильном экране массовые действия должны оставаться доступными при длинном roster.

Рекомендуемое представление — нижняя sticky action panel:

```text
[ ✓ Ожидаемые пришли     ]
[ Оставшиеся отсутствуют ]
[ Закрыть ведомость      ]
```

Sticky presentation является presentation concern: сама операция выполняется тем же application service, что и на desktop.

Действие:

```text
Ожидаемые пришли
```

обязательно требует явного подтверждения пользователя перед POST.

UI передаёт:

```text
confirmed = true
```

только после подтверждения.

## Safe area

Интерфейс должен учитывать системные safe areas мобильных устройств.

Особенно это относится к:

- нижней sticky action panel;
- верхней navigation bar;
- горизонтальным page paddings.

Reference implementation использует CSS environment variables:

```css
env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
```

и:

```html
<meta name="viewport"
      content="width=device-width, initial-scale=1, viewport-fit=cover">
```

## Sticky navigation и actions

Верхняя навигация может оставаться sticky.

Нижняя action panel на телефоне может оставаться sticky, пока доступны действия Attendance.

При переходе на более широкий экран sticky bottom panel может становиться обычной статической горизонтальной панелью.

Sticky элементы не должны перекрывать:

- последнюю карточку ученика;
- browser/system safe area;
- сообщения об ошибках;
- submit controls.

## Формы и ввод

Select, date input и login controls должны занимать доступную ширину на узком экране.

Основные формы не должны требовать pinch zoom.

Размер текста input должен оставаться достаточным, чтобы мобильные браузеры не выполняли нежелательный auto-zoom при фокусе.

## Состояния и обратная связь

После POST пользователь должен получить однозначную обратную связь:

- новое состояние визуально отображается после redirect;
- ValidationError показывается через messages framework;
- успешные массовые операции могут показывать число изменённых записей;
- отсутствие Coverage не блокирует PRESENT и отображается как `Без покрытия`.

PRG pattern:

```text
POST
  ↓
application service
  ↓
redirect
  ↓
GET с актуальным состоянием
```

предпочтителен для всех пользовательских действий.

## Accessibility baseline

Минимальные требования:

- controls доступны с клавиатуры;
- интерактивные элементы имеют заметный focus state;
- состояние не кодируется только цветом;
- основной текст сохраняет читаемый contrast;
- semantic `button`, `form`, headings и landmarks используются вместо click handlers на произвольных `div`;
- сообщения после действий доступны в области с `aria-live` или эквивалентным механизмом.

## Desktop / tablet

Desktop не является отдельным функциональным интерфейсом.

На широких экранах допускается:

- несколько колонок карточек;
- более плотные отступы;
- горизонтальное размещение action controls;
- статическая вместо sticky bottom action panel.

Нельзя создавать desktop-only действие, недоступное на телефоне, если оно относится к основному workflow тренера или пользователя.

# 57. Развёртывание

Минимальный production deployment:

```text
Reverse proxy
    │
    ▼
Django / Gunicorn
    │
    ▼
PostgreSQL
```

В Docker Compose это может выглядеть как:

```text
proxy
web
db
backup
```

Reverse proxy обязан **перезаписывать** `X-Real-IP` реальным адресом прямого
клиента. Приложение доверяет этому заголовку только когда непосредственный
`REMOTE_ADDR` входит в `TRUSTED_PROXY_IPS`; по умолчанию список пуст.
Приложение не использует `X-Forwarded-For` для Axes rate limiting.
`TRUSTED_PROXY_IPS` поддерживает отдельные IP и CIDR-сети, например
`172.18.0.0/16` для Docker Compose. Некорректные значения и пустой production
список обнаруживаются Django system checks как предупреждения.

IP-only lockout защищает от password spraying, но может временно блокировать
всех пользователей за общим NAT/public Wi-Fi после общего порога ошибок. Для
MVP это осознанный security trade-off; при необходимости production policy
может задать отдельный более высокий IP-only threshold через custom Axes
lockout policy.

Redis для первой версии не обязателен.

Его можно добавить позже для:

- фоновых задач;
- уведомлений;
- очередей;
- кеширования.

# 60. Изменение шаблона

Изменение:

```text
каждый вторник 18:00
```

не должно автоматически переписывать уже проведённые занятия.

ScheduleTemplate не редактируется in-place после начала использования.
Изменение создаёт новую версию шаблона с `valid_from = effective_from`, а
старую версию ограничивает `valid_until = effective_from - 1`, оставляя её
генерируемой до конца собственного интервала.

Versioning запрещается, если на `effective_from` и позже у старого шаблона
есть опубликованные/подтверждённые/завершённые занятия либо DRAFT с активным
LessonEnrollment или OneTimeEntitlement. Забронированный DRAFT нужно сначала
явно перенести через `reschedule_lesson`: DRAFT-reschedule разрешён и
cross-app workflow переносит активные LessonEnrollment и неиспользованные
OneTimeEntitlement на replacement. Replacement можно поставить сразу в будущий регулярный слот новой версии.

При генерации пересекающееся неотменённое занятие той же группы считается
покрытием регулярного слота **только если совпадает LessonType**. Если тип
отличается, генератор не пропускает регулярное занятие молча: записывается
`LessonGenerationConflict`, а management command завершает запуск ошибкой,
чтобы cron/monitoring заметили конфликт.

Если concrete Lesson самого ScheduleTemplate на этот `starts_at` уже
существует в любом статусе, включая CANCELLED, он считается явным решением
школы по этому слоту и проверка внешних пересечений для него не выполняется.
Повторный unresolved конфликт продолжает завершать cron ошибкой, но одинаковый
audit event для `template + expected_starts_at` не дублируется.

Только безопасные будущие DRAFT без броней автоматически переводятся в
CANCELLED.

# 63. Будущая интеграция оплаты

Будущий billing context содержит catalog/order/payment/refund. Продукт может создать Subscription, OneTimeEntitlement либо add-on charge без entitlement.

Индивидуальное занятие тарифицируется как `INDIVIDUAL_ICE + STUDENT_ICE_ADMISSION + COACH_ICE_ADMISSION`. Мини-группа — по текущему правилу те же компоненты на каждого участника. Только lesson component создаёт entitlement.

Пробный ICE стоит 50% обычного разового ICE; пробного HALL нет. `SKATE_RENTAL` является add-on и не влияет на Attendance/allowance.

# 66. Критические бизнес-инварианты

1. Один Attendance на Student+Lesson.
2. Один active AttendanceCoverage на Attendance.
3. RSVP не расходует entitlement.
4. ICE и HALL balances независимы.
5. One-time entitlement имеет приоритет над monthly allowance для своего Lesson.
6. `PRESENT → ABSENT` обращает именно использованное покрытие.
7. Attendance может быть PRESENT без покрытия.
8. Ledger immutable; ручная корректировка — `ADJUSTMENT` allowance.
9. Makeup не увеличивает купленный лимит.
10. Отмена Lesson сама по себе не создаёт CONSUME.

# 67. Транзакционность списания

```text
BEGIN
set Attendance=PRESENT
find exact one-time / makeup / ordinary allowance
if allowance-backed: LOCK SubscriptionAllowance, verify balance, CONSUME -1
create AttendanceCoverage
write AuditEvent
COMMIT
```

При ошибке вся операция rollback.

```text
allowance_balance = SUM(SubscriptionLedgerEntry.delta WHERE allowance_id=...)
```

Для смешанного тарифа UI агрегирует словарь `{ICE, HALL}`, а не одно число.

# 71. Пример полного жизненного цикла

Посещение ICE создаёт `CONSUME -1` только в ICE allowance; HALL остаётся неизменным. Исправление создаёт `RESTORE +1` в тот же allowance. Разовое/пробное посещение с OneTimeEntitlement monthly ledger не меняет.

# 75. Производительность

Предполагаемый объём даже для достаточно крупной школы мал для Django/PostgreSQL.

Например:

```text
500 участников
20 групп
50 занятий в неделю
2 600 занятий в год
```

Даже при нескольких годах истории PostgreSQL будет работать с таким объёмом без специальных архитектурных решений.

Микросервисы, Kubernetes и распределённая БД не требуются.

# 77. Acceptance Criteria MVP

MVP считается готовым, если выполняются следующие сценарии.

## Сценарий 1

Администратор создаёт:

```text
группу
тренера
расписание
```

и занятия появляются в календаре.

## Сценарий 2

Пользователь входит и видит только расписание своего участника.

## Сценарий 3

Пользователь может поставить:

```text
Буду
```

или:

```text
Не буду
```

## Сценарий 4

Организатор видит:

```text
12 будут
3 не будут
4 не ответили
```

## Сценарий 5

Тренер открывает занятие на телефоне и отмечает:

```text
Пришёл
```

## Сценарий 6

У участника имеется:

```text
8 занятий
```

после отметки присутствия становится:

```text
7 занятий.
```

## Сценарий 7

Повторное нажатие тренером не уменьшает остаток до 6.

## Сценарий 8

Если тренер исправляет присутствие на отсутствие:

```text
остаток 7 → 8.
```

## Сценарий 9

Если абонемента нет, присутствие всё равно сохраняется и появляется предупреждение администратору.

## Сценарий 10

После окончания срока действия оставшиеся занятия нельзя использовать новым посещением.

# 78. Предлагаемая последовательность разработки

После scheduling/attendance реализуются allowance-based subscriptions, immutable ledger, coverage engine, one-time entitlements и makeup flow; затем Admin/UI и будущий billing integration boundary.

# 79. Главный архитектурный принцип

```text
LessonResponse = намерение
Attendance = фактический приход
AttendanceCoverage = чем покрыт факт
SubscriptionAllowance / OneTimeEntitlement = право посещения
Billing = деньги (отдельный контекст)
```

Эти понятия не подменяют друг друга.
