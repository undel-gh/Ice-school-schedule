# Спецификация системы расписания, посещаемости и абонементов школы фигурного катания

**Версия:** 1.0  
**Стек:** Django + PostgreSQL + Django Admin + server-rendered frontend  
**Статус:** базовая спецификация MVP с возможностью дальнейшего расширения

---

# 1. Назначение системы

Система предназначена для организации расписания занятий школы фигурного катания, предварительного подтверждения участия учениками/родителями, фиксации фактической посещаемости тренерами и учёта абонементов.

Система должна заменить существующую схему, при которой расписание публикуется в чате, а участники ставят `+` или `-`.

Основные задачи:

1. Ведение групп, тренеров и расписания.
2. Публикация персонального расписания для каждого участника.
3. Возможность заранее отметить:
   - «Буду»;
   - «Не буду».
4. Отображение организатору ожидаемого количества участников.
5. Фиксация тренером фактического присутствия.
6. Учёт абонементов с ограниченным количеством занятий и сроком действия.
7. Автоматическое списание занятия из абонемента при фактическом посещении.
8. Отображение остатка абонемента.
9. Минимизация объёма персональных данных.
10. Возможность в будущем подключить оплату, не меняя основную архитектуру.

---

# 2. Основные принципы

## 2.1. Фактическое посещение отделяется от намерения прийти

В системе существуют два независимых понятия.

### RSVP

Ответ пользователя до занятия:

- буду;
- не буду;
- нет ответа.

RSVP используется для планирования количества участников.

Он **не списывает занятие из абонемента**.

### Attendance

Фактическая отметка тренера:

- присутствовал;
- отсутствовал;
- не отмечено.

Именно фактическое присутствие является основанием для расходования занятия из абонемента.

Таким образом:

```text
«Буду» → занятие не списывается.

Тренер отметил «Пришёл» → занятие списывается.
```

# 3. Архитектура

Система реализуется как единое Django-приложение.

```text
                  Пользователь
             телефон / ПК / планшет
                       │
                     HTTPS
                       │
                       ▼
              ┌─────────────────┐
              │     Django      │
              │                 │
              │ Server-rendered │
              │    frontend     │
              │                 │
              │  Business logic │
              │                 │
              │  Django Admin   │
              └────────┬────────┘
                       │
                       ▼
               ┌──────────────┐
               │ PostgreSQL   │
               └──────────────┘
```

Отдельное SPA на React/Vue в первой версии не требуется.

Frontend реализуется через:

- Django Templates;
- HTML;
- CSS;
- минимальный JavaScript;
- при необходимости HTMX.

Это уменьшает:

- количество компонентов;
- объём JavaScript;
- сложность авторизации;
- количество API;
- поверхность атаки;
- стоимость сопровождения.

# 4. Пользовательские роли

## 4.1. Участник / родитель

Может:

- войти через внешний Identity Provider;
- видеть расписание связанных с аккаунтом участников;
- переключаться между детьми, если их несколько;
- ставить «Буду» / «Не буду»;
- видеть состояние своего абонемента;
- видеть количество оставшихся занятий;
- видеть срок действия абонемента;
- видеть историю собственных посещений.

Не может:

- видеть других участников;
- видеть списки группы;
- изменять фактическую посещаемость;
- изменять абонемент.

# 5. Родитель и ребёнок

Учётная запись и занимающийся человек должны быть разными сущностями.

Например:

```text
Account
   │
   ├── Маша
   │     └── группа «Начальная 1»
   │
   └── Петя
         └── группа «Подготовительная»
```

Это позволяет использовать один аккаунт родителя для нескольких детей.

Отдельная учётная запись ребёнку не требуется.

Также допускается:

```text
Account → Participant
```

когда совершеннолетний участник самостоятельно пользуется системой.

---

# 6. Тренер

Тренер должен иметь специализированный интерфейс, не требующий работы непосредственно с Django Admin.

Тренер может:

- видеть сегодняшние занятия;
- видеть назначенные ему занятия;
- видеть участников соответствующей группы;
- видеть RSVP;
- отмечать фактическое присутствие;
- исправлять ошибочно поставленную отметку в пределах разрешённого периода.

Например:

```text
Лёд
14 сентября
17:00–18:00

Ожидалось: 12

─────────────────────────
Маша             ✓ Пришла
Катя              ✓ Пришла
Саша              ○ Отметить
Ира               ✕ Нет
Петя              ○ Отметить
─────────────────────────
```

Основное действие тренера:

**«Пришёл»**

При его нажатии система:

```text
1. фиксирует фактическое присутствие;
2. находит подходящий абонемент;
3. списывает одно занятие;
4. обновляет остаток.
```

Все операции выполняются в одной транзакции БД.

# 7. Администратор школы

Администратор имеет доступ к Django Admin и специализированным отчётам.

Он может управлять:

- участниками;
- аккаунтами;
- тренерами;
- группами;
- площадками;
- расписанием;
- типами занятий;
- абонементами;
- тарифами;
- фактической посещаемостью;
- корректировками списаний.

Также администратор видит ситуации, требующие внимания:

```text
Участник пришёл, но активного абонемента нет.

Абонемент закончился.

Абонемент просрочен.

Занятие отмечено задним числом.

Списание было отменено.

Остаток скорректирован вручную.
```

# 8. Типы занятий

В первой версии поддерживаются три основных типа:

```text
ICE
Лёд

CHOREOGRAPHY
Хореография

CONDITIONING
Физическая подготовка / ОФП
```

Типы рекомендуется хранить в отдельной сущности `LessonType`, а не жёстко кодировать в приложении.

Это позволит позже добавить:

- растяжку;
- прыжковую подготовку;
- индивидуальные занятия;
- сборы;
- мастер-классы.

---

# 9. Группы

Пример:

```text
Начальная 1
Начальная 2
Спортивная
Подготовительная
Взрослые
```

Участник может одновременно состоять в нескольких группах.

Связь:

```text
Participant
      │
      ▼
GroupMembership
      │
      ▼
Group
```

`GroupMembership` содержит:

- дату начала;
- дату окончания;
- признак активности.

Историческая принадлежность к группам не должна теряться.

# 10. Расписание

## 10.1. Шаблон расписания

Для регулярных занятий создаётся `ScheduleTemplate`.

Например:

```text
Группа: Начальная 1
Тип: Лёд
Тренер: Анна
День недели: Вторник
Начало: 18:00
Продолжительность: 60 минут
Площадка: Ледовый дворец
```

На основании шаблона создаются конкретные занятия.

---

# 11. Конкретное занятие

Каждое фактическое занятие — отдельный объект `Lesson`.

Например:

```text
Lesson #8172

22.09.2026
18:00–19:00

Лёд
Начальная 1
Анна
```

Именно с `Lesson` связываются:

- RSVP;
- Attendance;
- списания абонемента.

Это позволяет изменить одно занятие, не затрагивая остальные.

Например:

```text
22 сентября:
18:00 → 19:00
```

не изменяет занятия 29 сентября и 6 октября.

---

# 12. Статусы занятия

Рекомендуемые статусы:

```text
SCHEDULED
Запланировано

CANCELLED
Отменено

COMPLETED
Проведено
```

Дополнительно можно предусмотреть:

```text
RESCHEDULED
Перенесено
```

но технически перенос можно представить как изменение времени занятия с сохранением журнала изменений.

Отменённое занятие не должно расходовать абонементы.

---

# 13. RSVP

Модель:

`LessonResponse`

Ключевые поля:

```text
id
lesson_id
participant_id

status:
    YES
    NO

updated_at
updated_by
```

Отсутствие записи означает:

```text
NO_RESPONSE
```

В БД должна существовать уникальность:

```text
lesson + participant
```

---

# 14. Фактическая посещаемость

Модель:

`Attendance`

Поля:

```text
id
lesson_id
participant_id

status:
    PRESENT
    ABSENT

marked_at
marked_by
```

До выставления отметки запись может отсутствовать.

Уникальность:

```text
lesson + participant
```

---

# 15. Ключевое правило списания

**Одно посещение = одно списание из абонемента**, если тарифом явно не установлено иное.

Списание происходит только при:

```text
Attendance.status = PRESENT
```

RSVP на списание не влияет.

---

# 16. Абонементы

Необходимо разделить:

```text
SubscriptionPlan
```

и

```text
Subscription
```

## SubscriptionPlan

Это тип абонемента.

Например:

> 8 занятий / месяц

или:

> 12 занятий / 45 дней.

## Subscription

Это конкретный абонемент конкретного участника.

Например:

> Абонемент Маши  
> 8 занятий  
> с 01.09.2026 по 30.09.2026.

---

# 17. Модель тарифа абонемента

`SubscriptionPlan`

Поля:

```text
id
name
description

visit_count

validity_type
default_validity_value

is_active
```

Пример:

```text
name:
    «8 занятий / месяц»

visit_count:
    8

validity_type:
    CALENDAR_MONTH

default_validity_value:
    1
```

---

# 18. Срок действия

Конкретный `Subscription` всегда должен иметь явные:

```text
starts_on
expires_on
```

Например:

```text
01.09.2026
        ↓
30.09.2026
```

Это намного надёжнее, чем вычислять срок действия каждый раз из тарифа.

Тариф определяет только значения по умолчанию при создании абонемента.

---

# 19. Варианты срока действия

Архитектура должна предусматривать:

### Calendar period

Например:

> 8 занятий в течение календарного месяца.

```text
01.09 → 30.09
```

### Fixed duration

Например:

> 8 занятий в течение 30 дней.

```text
12.09 → 11.10
```

### Manual

Администратор вручную задаёт:

```text
starts_on
expires_on
```

Для первой версии достаточно реализовать:

- календарный месяц;
- фиксированное количество дней;
- ручной период.

---

# 20. Ограничение абонемента по занятиям

Не каждый абонемент обязательно должен работать на все виды занятий.

Необходимо предусмотреть ограничения:

```text
SubscriptionPlan
        │
        ├── разрешённые LessonType
        │
        └── разрешённые Group
```

Например:

> «8 тренировок на льду»

покрывает только:

```text
ICE
```

Другой тариф:

> «8 любых групповых занятий»

может покрывать:

```text
ICE
CHOREOGRAPHY
CONDITIONING
```

---

# 21. Остаток абонемента

Нельзя использовать модель:

```text
remaining_visits = 5
```

и просто менять число при посещении.

Это создаёт риск рассинхронизации.

Например:

```text
было 5
списали → 4
отменили посещение
забыли вернуть → осталось 4
```

Вместо этого используется журнал операций.

---

# 22. Журнал операций абонемента

Модель:

`SubscriptionLedgerEntry`

Каждая операция содержит изменение количества доступных занятий.

Пример:

```text
+8  Выдан абонемент
-1  Посещение 5 сентября
-1  Посещение 8 сентября
-1  Посещение 12 сентября
+1  Возврат ошибочного списания
```

Остаток:

```text
SUM(delta)
```

В данном случае:

```text
8 - 1 - 1 - 1 + 1 = 6
```

---

# 23. Типы операций

```text
GRANT
Выдача занятий

CONSUME
Списание

RESTORE
Возврат

ADJUSTMENT
Ручная корректировка
```

Поля:

```text
id
subscription_id

delta

entry_type

lesson_id
attendance_id

reason

created_at
created_by
```

Например:

```text
delta = -1
entry_type = CONSUME
lesson = 5 сентября, лёд
```

---

# 24. История абонемента

Пользователь может видеть:

```text
Абонемент
8 занятий

Действует:
01.09–30.09

Осталось:
5 из 8

История

05.09  Лёд             −1
08.09  Хореография     −1
12.09  Лёд             −1
```

Платёжную информацию здесь выводить не требуется.

---

# 25. Выбор абонемента при посещении

У одного участника одновременно может существовать несколько абонементов.

При отметке:

```text
«Пришёл»
```

система должна найти подходящий абонемент.

Проверяются:

1. участник;
2. дата занятия входит в период действия;
3. абонемент активен;
4. тип занятия разрешён;
5. группа разрешена, если установлено ограничение;
6. имеется положительный остаток.

Если подходит несколько абонементов, используется следующий порядок:

```text
1. раньше заканчивается;
2. раньше начинается;
3. раньше создан.
```

Таким образом система в первую очередь расходует абонемент, который скоро истечёт.

---

# 26. Важное правило даты

Проверка срока действия выполняется относительно:

**даты занятия**, а не даты, когда тренер поставил отметку.

Например:

```text
Занятие:
30 сентября

Абонемент:
до 30 сентября

Тренер поставил отметку:
1 октября
```

Занятие должно быть списано, поскольку на момент проведения занятия абонемент был действующим.

---

# 27. Отсутствие действующего абонемента

Отсутствие абонемента не должно мешать тренеру отметить реальное присутствие.

Например:

```text
Маша → ПРИСУТСТВОВАЛА
```

фиксируется в любом случае.

Но система создаёт состояние:

```text
UNCOVERED ATTENDANCE
```

или эквивалентный признак:

> Посещение не покрыто абонементом.

Администратор получает такую запись в отдельном отчёте.

Позже он может:

- назначить новый абонемент;
- выбрать существующий абонемент вручную;
- оставить занятие бесплатным;
- произвести ручную корректировку.

---

# 28. Исправление ошибки тренера

Сценарий:

```text
Тренер:
ПРИШЁЛ
```

Система:

```text
Attendance = PRESENT
Subscription = #123
Ledger = -1
```

Затем выясняется, что участника не было.

Тренер или администратор меняет:

```text
PRESENT → ABSENT
```

Система автоматически создаёт:

```text
RESTORE +1
```

именно в тот абонемент, из которого было исходное списание.

В результате история сохраняется:

```text
-1 посещение
+1 исправление ошибочного посещения
```

а предыдущая операция не удаляется.

---

# 29. Защита от двойного списания

Необходимо гарантировать, что повторное нажатие кнопки:

```text
«Пришёл»
```

не сможет списать два занятия.

На уровне PostgreSQL должна быть уникальность для списания одного посещения.

Логически:

```text
attendance_id + CONSUME
```

может существовать только один раз.

Операция должна выполняться через:

```text
transaction.atomic()
```

с блокировкой изменяемых записей при необходимости.

---

# 30. Отмена занятия

Если занятие отменено:

```text
Lesson.status = CANCELLED
```

оно:

- не должно отображаться как обычное предстоящее занятие;
- не должно расходовать абонементы;
- должно отображаться пользователю как отменённое.

Если по ошибке посещения уже были отмечены, система должна потребовать их обработки или автоматически сформировать возвраты.

---

# 31. No-show

В базовой версии:

```text
ответил «Буду»
        +
не пришёл
        =
занятие НЕ списывается.
```

То есть оплачивается/расходуется только фактическое посещение.

В будущем `SubscriptionPlan` можно расширить политикой:

```text
no_show_policy
```

например:

- не списывать;
- списывать при отмене позже определённого времени;
- списывать всегда.

Но это не требуется для MVP.

# 66. Критические бизнес-инварианты

Система должна гарантировать:

### 1.

Один участник не может иметь две записи Attendance для одного занятия.

### 2.

Одно посещение не может дважды списать абонемент.

### 3.

RSVP никогда сам по себе не расходует абонемент.

### 4.

`PRESENT → ABSENT` возвращает ранее списанное занятие.

### 5.

Возврат производится в исходный абонемент.

### 6.

Срок действия проверяется относительно даты занятия.

### 7.

Фактическое присутствие можно сохранить даже без подходящего абонемента.

### 8.

История списаний не удаляется для исправления остатка.

### 9.

Ручная корректировка всегда создаёт Ledger Entry.

### 10.

Отмена занятия не должна уменьшать остаток абонемента.

# 67. Транзакционность списания

Логика отметки присутствия должна выполняться примерно как единая операция:

```text
BEGIN

создать/изменить Attendance

если PRESENT:
    найти подходящий Subscription

    если найден:
        заблокировать Subscription
        проверить balance
        создать CONSUME -1

    иначе:
        отметить attendance как uncovered

COMMIT
```

При ошибке:

```text
ROLLBACK
```

Не допускается состояние:

```text
Attendance = PRESENT

но операция списания
завершилась только наполовину.
```

---

# 68. Расчёт баланса

Авторитетным источником является ledger.

Концептуально:

```text
balance =
SUM(SubscriptionLedgerEntry.delta)
```

Можно добавить кешированное поле:

```text
cached_balance
```

только если позднее возникнут проблемы производительности.

Для первоначального объёма школы это не требуется.

---

# 69. Работа с просроченным остатком

Пример:

```text
Абонемент:
8 занятий

Использовано:
6

Осталось:
2

Дата окончания:
30 сентября
```

После 30 сентября:

```text
остаток физически остаётся в истории = 2
```

но использовать его нельзя.

Не нужно создавать искусственную операцию:

```text
-2 EXPIRED
```

если нет отдельной бизнес-причины.

Система просто определяет:

```text
expires_on < lesson.date
```

и не считает абонемент подходящим.

Это сохраняет корректную историческую информацию:

> из восьми занятий реально было использовано шесть.

# 76. Тестирование

Обязательные unit/integration tests:

### Attendance

- присутствие сохраняется;
- отсутствие сохраняется;
- повторное нажатие не создаёт второе списание.

### Subscription

- корректно считается баланс;
- нельзя списать просроченный абонемент;
- нельзя использовать абонемент не для того типа занятия;
- выбирается наиболее подходящий абонемент.

### Correction

- PRESENT → ABSENT создаёт RESTORE;
- повторное исправление не создаёт несколько возвратов.

### Access control

- родитель не видит чужого ребёнка;
- тренер не видит чужую группу;
- обычный пользователь не имеет доступа к Admin.

### Schedule

- шаблон создаёт занятия;
- повторная генерация не создаёт дубликаты.

У участника имеется:

После окончания срока действия оставшиеся занятия нельзя использовать новым посещением.

# 79. Главный архитектурный принцип

Расписание, фактическое присутствие и финансовое право на посещение не должны быть одной сущностью.

Правильная модель:

```text
          Lesson
         /      \
        /        \
     RSVP      Attendance
                   │
                   │ PRESENT
                   ▼
             Subscription
                   │
                   ▼
                 Ledger
```

Это даёт возможность независимо отвечать на три разных вопроса:

```text
Планирует ли человек прийти?

Пришёл ли он фактически?

Каким абонементом оплачивается это посещение?
```

Такое разделение должно сохраняться и при дальнейшем развитии системы.
